# DEL I – EKSAMENEN OG STRATEGIEN

## 1. Hva er REA3050?

REA3050 er fagkoden for Informasjonsteknologi 2, muntlig-praktisk. Ifølge Utdanningsdirektoratet er eksamen lokalt utarbeidet og lokalt sensurert. For privatister er REA3050 obligatorisk sammen med skriftlig REA3049 for å få fullført faget. Oppgaven og vurderingen tar utgangspunkt i læreplanen INF01-03. Det betyr at det ikke finnes én nasjonal, identisk muntlig oppgave som alle kandidater får.

Det viktigste å forstå er forskjellen mellom **å kunne gjengi teori** og **å vise kompetanse**. Sensor ønsker ikke bare å høre definisjonen av en klasse eller en algoritme. Du må kunne bruke begrepene til å forklare en løsning, beskrive hvordan noe fungerer, vurdere alternativer, demonstrere en ferdighet og reflektere over kvaliteten på resultatet.

En god eksamensbesvarelse kan for eksempel handle om et program for et bibliotek. Du må ikke bare si at programmet har en klasse `Bok`. Du bør kunne forklare hvorfor det er nyttig å modellere bøker som objekter, hvilke egenskaper hvert bokobjekt har, hvilke metoder som trengs, hvordan utlån kan modelleres, hvordan du tester programmet, hvordan data lagres, hvilke personopplysninger systemet behandler, og hvordan løsningen kan forbedres for brukeren.

## 2. Hva vet vi om den lokale muntlig-praktiske gjennomføringen?

### 2.1 Oslo – opplysningene som er funnet for høsten 2026

Oslo Privatistkontors oppdaterte retningslinjer for muntlig og muntlig-praktisk eksamen (H26) sier i hovedtrekk:

- Kandidaten trekker ett av flere oppgavesett.
- Etter oppgavetrekk får kandidaten minst 30 minutter til forberedelse.
- Alle hjelpemidler er tillatt i forberedelsestiden, bortsett fra hjelpemidler som forstyrrer andre kandidater.
- Kandidaten kan ta med egen datamaskin til forberedelsesrommet, men har selv ansvar for maskin, programvare og strøm. Privatistkontoret garanterer ikke internettilgang eller teknisk hjelp.
- Notater må skrives på papir som finnes i forberedelsesrommet. Notater laget hjemme kan ikke brukes under selve eksaminasjonen.
- Notatene kan tas med inn og brukes som støtte, men de skal ikke vurderes. Å lese direkte fra notatene kan virke negativt.
- Oppgavene skal være åpne og ta utgangspunkt i sentrale temaer knyttet til kompetansemålene.
- Den praktiske delen skal fremgå av oppgaven. Praktisk innslag kan være demonstrasjon/forsøk eller at kandidaten forklarer eller tegner på papir for å vise ferdigheter.
- Sensor kan stille oppklarende, utdypende og utvidende spørsmål.
- Kandidaten får også en tilleggsoppgave som prøver andre kompetansemål enn oppgaven som ble trukket. Tilleggsoppgaven skal ikke være kjent i forberedelsestiden.
- Muntlig-praktisk eksamen varer inntil 45 minutter.
- Eksaminasjonen er en fagsamtale. Før forberedelsen avklares det om kandidaten starter med å fortelle om temaet eller om samtalen starter direkte.
- PowerPoint eller tilsvarende presentasjon skal ikke brukes.
- Kandidaten trenger ikke eget utstyr inne i eksamensrommet med mindre det står i eksamensbeskrivelsen i Privatistportalen.
- Kandidater eksamineres én og én. Det kan gå opptil omtrent 4,5 timer fra oppmøte til alle på partiet er ferdige; ventetid må påregnes.

**Viktig:** Informasjonsskrivet og detaljene i Privatistportalen for akkurat din eksamen har forrang dersom noe av dette avviker. Ta med gyldig legitimasjon, egne skrivesaker og nødvendig utstyr til forberedelsesdelen. Sjekk e-post og Privatistportalen før eksamen.

### 2.2 Andre fylker kan organisere forberedelsen annerledes

Østfold fylkeskommune har publisert en kurs-/fagspesifikk rammebeskrivelse for REA3050. Der er forberedelsestiden 48 timer. Privatisten får en sammensatt oppgave med flere delmomenter som skal berøre mange kjerneelementer og flertallet av kompetansemålene. Eksamen varer inntil 45 minutter. Kandidaten kan bruke inntil 15 minutter på å presentere, forklare og begrunne utviklingsarbeidet fra forberedelsen. Resten er dialog med utdyping, begrunnelse og praktisk demonstrasjon. Det kan også stilles spørsmål fra andre deler av læreplanen dersom kandidaten ikke har vist nok kompetanse innenfor det trukne temaet.

Dette er et nyttig eksempel på en mulig lokal eksamensmodell, men **det er ikke Oslo-reglene**. Ikke forbered deg på 48 timer med mindre Privatistportalen eller informasjonsskrivet ditt sier det.

### 2.3 Finnes tidligere muntlige REA3050-oppgaver offentlig?

Det ble søkt etter tidligere oppgaver for REA3050, eksempeloppgaver, sensorveiledninger og omtaler av gjennomførte muntlige eksamener. Oslo kommune opplyser uttrykkelig at tidligere gitte oppgaver til muntlig, praktisk og muntlig-praktisk privatisteksamen ikke publiseres. Det finnes dermed ikke et pålitelig offentlig arkiv med tidligere Oslo-oppgaver som kan brukes som fasit for hva som kommer 30. november.

Det som er offentlig tilgjengelig, er særlig:

1. Udirs læreplan og kompetansemål.
2. Udirs generelle rammer for muntlig og muntlig-praktisk eksamen.
3. Fylkeskommunale rammedokumenter som beskriver hvordan oppgaver kan bygges opp.
4. Tidligere **skriftlige** IT2-eksamener. Disse er ikke muntlige eksamensoppgaver, men viser faglige problemtyper som egner seg til praktiske og muntlige overføringsøvelser.

Oppgavene i denne pakken er derfor **originale treningsoppgaver** utformet fra kompetansemålene og offentlig eksamensinformasjon. De skal ikke omtales som tidligere ekte eksamensoppgaver.

## 3. Hva vurderes?

Det er kompetansen du viser på eksamensdagen som vurderes. Forberedelsesdelen er en hjelp til å forberede deg, men notatene i seg selv får ikke karakter. Du kan derfor ikke basere deg på å ha produsert mange sider notater eller en ferdig løsning hvis du ikke klarer å forklare, anvende og begrunne arbeidet.

Sensorene må gi kandidaten mulighet til å vise kompetanse i så stor del av faget som eksamensformen tillater. Oppgaven er åpen for at kandidaten skal kunne ta egne valg. Sensor kan bevege seg fra den konkrete oppgaven til andre relevante kompetansemål.

En muntlig-praktisk eksamen kan derfor teste flere evner i samme samtale:

- **Begrepsforståelse:** Kan du forklare hva sentrale fagbegreper betyr?
- **Anvendelse:** Kan du bruke kunnskapen til å løse et konkret problem?
- **Modellering:** Kan du beskrive systemet før eller mens du lager løsningen?
- **Programmering:** Kan du lese, skrive, endre eller forklare kode?
- **Testing:** Kan du undersøke om løsningen fungerer, og forklare hvordan du vet det?
- **Vurdering:** Kan du sammenligne alternativer og forklare hvorfor du valgte én løsning?
- **Refleksjon:** Kan du se begrensninger, risikoer og konsekvenser?
- **Formidling:** Kan du forklare arbeidet slik at sensor forstår hva du har gjort og hvorfor?

## 4. Hva betyr karakter 2, 3 og 4 i denne treningsplanen?

Udir beskriver karakter 2 som lav kompetanse, karakter 3 som nokså god kompetanse og karakter 4 som god kompetanse. Dette er de generelle karakteruttrykkene. Det finnes ikke en offentlig nasjonal REA3050-sensorveiledning som gjør at vi kan regne ut en bestemt karakter fra en quizscore.

Denne pakken bruker derfor en **treningsrubrikk**, ikke en offisiell karakterformel:

### Nivå 2 – minimumskompetanse

Kandidaten kjenner igjen sentrale begreper og viser noe relevant forståelse. Kandidaten kan utføre enkelte grunnleggende handlinger, men trenger ofte støtte, har hull i forklaringene eller har vansker med å knytte teori til praktisk arbeid.

Et offentlig eksempel på mer konkrete REA3050-kriterier finnes hos Trøndelag fylkeskommune. Der beskrives lav kompetanse (karakter 2) blant annet som at kandidaten «til en viss grad» kan forklare metoder for design og implementering, objektorientert modellering, gjenbrukbar kode og systemutviklingsmetoder; «i noen grad» kan vise forståelse for hvordan IT påvirker samfunnet og drøfte etikk, personvern og informasjonssikkerhet; og «til en viss grad» kan forklare programmeringsteknikker, OOP, dataanalyse og sikker lagring/utveksling. Dette gir et nyttig, konkret bilde av et mulig lavt måloppnåelsesnivå, men kriteriene er fra Trøndelag og er **ikke bindende for Oslo**. På din eksamen er kriteriene som følger oppgavesettet og eksamensstedets regler styrende.

### Nivå 3 – nokså god kompetanse

Kandidaten forklarer sentrale begreper med egne ord, kan gjennomføre en enkel løsning, kan vise grunnleggende testing og kan gi relevante eksempler. Kandidaten kan gjøre noen feil, men viser at hovedideen er forstått og kan korrigere deler av arbeidet.

### Nivå 4 – god kompetanse og ønsket sikkerhetsmargin

Kandidaten arbeider selvstendig med relevante problemstillinger, bruker fagbegreper presist, forklarer hvorfor en løsning fungerer, vurderer minst ett alternativ, gjennomfører relevante tester, oppdager begrensninger og kan foreslå forbedringer. Kandidaten overfører kunnskapen til nye situasjoner og kan svare på oppfølgingsspørsmål uten å være avhengig av et innøvd manus.

**Målet nå er å sikre grunnleggende kompetanse på nivå 2 i alle sentrale deler, med noe ekstra trening på kode, testing og forklaring slik at én svak oppgave ikke velter hele prestasjonen. Dette er en treningsstrategi, ikke en garanti for karakter 2.**

# DEL II – LÆREPLANEN OG KOMPETANSEMÅLENE

## 5. De 11 kompetansemålene i IT2

Læreplanen INF01-03 har 11 kompetansemål etter Informasjonsteknologi 2. De skal forstås i lys av teksten «Om faget» og de fire kjerneelementene. Under er målene forklart som konkrete ferdigheter kandidaten kan vise.

### Mål 1 – Utforske og vurdere muligheter, utfordringer og konsekvenser ved bruk av informasjonsteknologi i ulike sammenhenger

Du må kunne forklare hvordan teknologi påvirker mennesker, virksomheter og samfunn. Du bør kunne analysere et konkret system og diskutere gevinster, ulemper, risiko, tilgjengelighet, personvern, kostnader og miljøpåvirkning.

Eksempel: Et digitalt køsystem kan redusere ventetid og gi bedre oversikt, men kan samtidig ekskludere personer uten smarttelefon, samle inn data om besøkende eller bli utilgjengelig ved nettverksfeil.

### Mål 2 – Drøfte etiske dilemmaer som oppstår som en konsekvens av informasjonsteknologi, både for individ og samfunn

Du må kunne presentere flere sider av et dilemma, identifisere interessenter, vurdere konsekvenser og begrunne en konklusjon. Det er ikke nok å si «det er bra» eller «det er dårlig».

Eksempel: Kameraovervåking kan beskytte personer og eiendom, men kan redusere privatliv, skape maktubalanse og føre til feilaktige mistanker eller formålsutglidning.

### Mål 3 – Utforske og vurdere alternative løsninger for design og implementering av et program

Du må kunne foreslå mer enn én mulig måte å løse et problem på og sammenligne dem. Det kan handle om brukergrensesnitt, algoritme, datastruktur, programarkitektur, lagringsformat, sikkerhet eller hvordan oppgaven deles opp.

Eksempel: Et lagerprogram kan lagre data i en enkel CSV-fil, en JSON-fil eller en relasjonsdatabase. Valget avhenger av datamengde, relasjoner, flere samtidige brukere og behovet for søk og oppdateringer.

### Mål 4 – Anvende objektorientert modellering til å beskrive et programs struktur

Du må kunne gå fra en tekstlig oppgave til en modell med klasser, attributter, metoder og relasjoner. Du bør forstå klassediagram, assosiasjon, arv, komposisjon og multiplisitet.

Eksempel: Et bibliotek kan modelleres med klassene `Bok`, `Medlem`, `Lån` og `Bibliotek`. Et lån knytter ett medlem til én bok i en gitt tidsperiode.

### Mål 5 – Utvikle objektorienterte programmer med klasser, objekter, metoder og arv

Du må kunne skrive eller demonstrere et program med klasser og objekter, forklare hva objektene representerer, og bruke metoder og arv når det passer. Du må kunne forklare hvordan data og funksjonalitet henger sammen.

### Mål 6 – Vurdere og bruke strategier for feilsøking og testing av programkode

Du må kunne identifisere feil, lage relevante testtilfeller, gjennomføre tester, tolke resultater og forbedre koden. Du må kjenne forskjellen på syntaksfeil, kjøretidsfeil og logiske feil.

### Mål 7 – Generalisere løsninger ved å utvikle og bruke gjenbrukbar programkode

Du må kunne unngå unødvendig kopiering ved å lage funksjoner, metoder, klasser eller moduler som kan brukes flere steder. Du må forstå parametere, returverdier, abstraksjon og modularitet.

### Mål 8 – Vurdere brukervennligheten i egne og andres programmer og foreslå forbedringer

Du må kunne undersøke om programmet er enkelt, effektivt og forståelig å bruke, og foreslå konkrete endringer. Du bør kunne forklare tilbakemeldinger, konsistens, tilgjengelighet, feilhåndtering og testing med brukere.

### Mål 9 – Velge og bruke relevante systemutviklingsmetoder og -verktøy for samarbeid med andre

Du må kunne forklare hvordan et utviklingsarbeid planlegges, fordeles, dokumenteres og forbedres. Du bør kjenne til smidig utvikling, fossefallsmodell, Scrum, versjonskontroll og verktøy for samarbeid.

### Mål 10 – Gjøre rede for standarder for lagring, utveksling og sikring av ulike typer data

Du må kunne forklare hvorfor data må representeres og lagres på bestemte måter, og hvordan data utveksles mellom systemer. Eksempler er CSV, JSON, XML, SQL-databaser, tegnkoding, HTTP/HTTPS, kryptering, tilgangskontroll og sikkerhetskopiering.

### Mål 11 – Bruke programmering til å innhente, analysere og presentere informasjon fra reelle datasett

Du må kunne hente data fra en fil eller kilde, undersøke og rydde dataene, beregne relevante resultater og presentere dem i tabeller eller diagrammer. Du må kunne vurdere datakvalitet og forklare hva resultatene betyr – og ikke betyr.

## 6. Kjerneelementene

### Kreativ problemløsing

Du skal kunne bruke ulike metoder og verktøy for å løse både kjente og ukjente problemer. Det innebærer å prøve ut en løsning, undersøke resultatet, oppdage svakheter og endre strategi. På eksamen bør du vise at du ikke bare følger én oppskrift, men kan resonnere deg frem til en løsning når oppgaven er litt annerledes enn eksemplene du har øvd på.

### Teknologi, individ og samfunn

Du må se teknologi i en større sammenheng. En teknisk løsning påvirker mennesker, arbeidsliv, maktforhold, miljø, personvern, tilgjengelighet og samfunnsdeltakelse. Du skal kunne drøfte både nytte og risiko.

### Modellering og programmering

Du skal kunne lage modeller av informasjonssystemer og omsette dem til programkode. Modellering handler om å forenkle virkeligheten på en måte som er nyttig for systemet. Programmering handler om å gjøre modellen operativ.

### Digital representasjon og informasjonsutveksling

Du skal forstå hvordan data representeres, lagres, oppdateres, hentes frem og utveksles mellom mennesker og systemer. Det omfatter både tekniske formater og konteksten som gjør data meningsfulle.

## 7. Handlingsverbene – hva sensor ber deg gjøre

- **Utforske:** Undersøke, prøve ut, eksperimentere, stille spørsmål og finne informasjon.
- **Vurdere:** Veie fordeler og ulemper, bedømme kvalitet og ta begrunnet stilling.
- **Drøfte:** Belyse flere sider, argumentere for og imot og gjerne konkludere.
- **Anvende:** Bruke kunnskap i en praktisk eller konkret situasjon.
- **Beskrive:** Gjengi en situasjon eller struktur med relevante fagbegreper.
- **Utvikle:** Designe, lage eller forbedre en løsning.
- **Bruke:** Ta i bruk en metode eller et verktøy for å nå et mål.
- **Gjøre rede for:** Gi en faglig begrunnet forklaring.
- **Analysere:** Dele opp, undersøke sammenhenger og tolke betydning.
- **Presentere:** Vise, forklare eller demonstrere et faglig emne eller produkt.

**Eksamenstips:** Når du får et spørsmål som begynner med «vurder», ikke stopp ved definisjonen. Når spørsmålet sier «drøft», må du vise minst to sider. Når det sier «anvend», må du gjøre noe med kunnskapen – kode, modellere, teste eller bruke data.

# DEL III – GRUNDIG FAGSTOFF

# KAPITTEL 1 – INFORMASJONSTEKNOLOGI, INFORMASJONSSYSTEMER OG SAMFUNN

## 1.1 Hva er informasjonsteknologi?

Informasjonsteknologi (IT) handler om å bruke datamaskiner, programvare, nettverk og digitale systemer til å samle inn, lagre, behandle, presentere og utveksle informasjon. IT er mer enn en PC eller en app. Et informasjonssystem består vanligvis av flere deler som må fungere sammen:

1. **Maskinvare:** Fysiske komponenter som PC, mobil, server, sensor, skriver, ruter og lagringsenhet.
2. **Programvare:** Operativsystemer, apper, databaser, nettsider og tjenester.
3. **Data:** Verdier, tekst, bilder, lyd, video og registreringer som systemet behandler.
4. **Mennesker:** Brukere, administratorer, utviklere, kunder og andre interessenter.
5. **Prosesser:** Reglene og arbeidsflytene som beskriver hva som skal skje.
6. **Nettverk og kommunikasjon:** Forbindelser som lar komponenter utveksle data.

Et system kan være teknisk fungerende, men likevel mislykkes hvis brukerne ikke forstår det, dataene er feil, rutinene ikke passer eller sikkerheten er for svak.

### Eksempel: Digitalt bestillingssystem

En restaurant bruker en nettbasert løsning for bestilling. Kunden velger mat på en nettside. Nettleseren sender en forespørsel til en server. Serveren validerer bestillingen og lagrer den i en database. Kjøkkenet ser bestillingen på en skjerm. Kunden kan få en bekreftelse.

- Maskinvare: mobil, nettbrett, server og kjøkkenskjerm.
- Programvare: nettside, serverprogram og databaseprogram.
- Data: meny, priser, kundeinformasjon og bestillinger.
- Mennesker: kunde, servitør, kokk og administrator.
- Prosesser: bestille, bekrefte, tilberede, hente og betale.

Hvis nettverket faller ut, kan bestillinger slutte å komme frem selv om serveren fungerer. Hvis menyen ikke oppdateres, kan kunden bestille noe som ikke finnes. Hvis systemet samler inn unødvendig mye kundeinformasjon, oppstår personvernrisiko.

## 1.2 Data, informasjon og kunnskap

- **Data** er rå registreringer, for eksempel `18`, `2026-11-22`, `Oslo` eller `true`.
- **Informasjon** oppstår når data settes i sammenheng, for eksempel «temperaturen i Oslo var 18 °C kl. 14».
- **Kunnskap** er forståelse som gjør at vi kan tolke informasjon og ta en beslutning, for eksempel å vite at 18 °C er relativt varmt for november.

Data uten kontekst kan misforstås. Et tall som `18` sier lite uten enhet, tidspunkt og betydning. Et datasett med kolonnen `temp` bør derfor forklare om verdien er Celsius eller Fahrenheit, og hvor målingen ble gjort.

## 1.3 Muligheter ved IT

**Effektivisering:** Automatisering kan redusere manuelt arbeid, repetisjon og behandlingstid. Et digitalt bestillingssystem kan sende informasjon direkte til kjøkkenet.

**Tilgjengelighet:** Tjenester kan brukes hjemmefra og utenfor åpningstid. Digital helseinformasjon kan gjøre det enklere å kommunisere med helsevesenet.

**Bedre beslutninger:** Analyse av store datamengder kan avdekke mønstre, flaskehalser og behov.

**Kommunikasjon og samarbeid:** Skylagring, videomøter og versjonskontroll gjør at mennesker kan samarbeide på tvers av steder.

**Nye tjenester:** IT muliggjør digitale betalinger, strømming, netthandel, navigasjon og læringsplattformer.

## 1.4 Utfordringer og negative konsekvenser

**Digitalt utenforskap:** Ikke alle har like god tilgang til utstyr, nettverk, språk, digitale ferdigheter eller universelt utformede løsninger.

**Personvern:** Systemer kan samle inn mer informasjon enn nødvendig, koble data sammen og lage profiler av mennesker.

**Sikkerhet:** Feil konfigurasjon, svake passord, skadevare eller menneskelige feil kan føre til tap eller lekkasje av data.

**Avhengighet:** Når en virksomhet blir avhengig av et digitalt system, kan nedetid stoppe viktige tjenester.

**Automatiseringsfeil og skjevhet:** Algoritmer kan gi feilaktige eller diskriminerende resultater dersom data eller regler er skjeve.

**Miljø:** Produksjon av elektronikk krever råvarer og energi. Datasentre bruker strøm og kjøling. Hyppig utskifting øker elektronisk avfall.

## 1.5 Slik vurderer du konsekvenser systematisk

Når sensor ber deg vurdere et IT-system, bruk denne strukturen:

1. Hvem er interessentene? Brukere, ansatte, eiere, leverandører, myndigheter og personer som blir påvirket indirekte.
2. Hvilket behov skal systemet løse?
3. Hvilke fordeler gir systemet på kort og lang sikt?
4. Hvilke ulemper, risikoer og kostnader finnes?
5. Hvem får fordeler, og hvem kan bli skadelidende?
6. Hvilke tiltak kan redusere risikoen?
7. Hva er din begrunnede konklusjon?

### Gjennomarbeidet eksempel: Digitalt adgangssystem på skole

En skole vurderer å erstatte fysiske nøkler med adgangskort som loggfører når ansatte og elever går inn og ut.

**Fordeler:** Kort kan sperres raskt, tapte nøkler er mindre problematiske, skolen kan styre tilgang til ulike områder, og det kan bli lettere å undersøke uautorisert adgang.

**Ulemper:** Loggene kan vise bevegelsesmønstre. Hvis de brukes til å kontrollere elever eller ansatte uten tydelig formål, blir inngrepet større. Systemet kan feile ved strømbrudd eller nettverksproblemer. Elever kan glemme kortet.

**Mulige tiltak:** Samle bare nødvendige logger, begrense hvem som kan se dem, slette dem etter en fastsatt periode, informere brukerne, ha rutiner ved systemfeil og sørge for alternative adgangsløsninger.

**Konklusjon:** Et adgangssystem kan være nyttig, men må utformes slik at sikkerhetsgevinsten står i rimelig forhold til personverninngrepet. Loggene bør ikke brukes til andre formål uten selvstendig vurdering og lovlig grunnlag.

### Oppgaver – kapittel 1

**Grunnleggende**
1. Forklar forskjellen på data, informasjon og kunnskap. Bruk ett eksempel.

# KAPITTEL 2 – ETIKK, PERSONVERN OG SAMFUNNSKONSEKVENSER

## 2.1 Hva er et etisk dilemma?

Et etisk dilemma oppstår når flere hensyn står mot hverandre, og ingen løsning ivaretar alle verdier fullt ut. Det er ofte forskjell mellom hva som er lovlig, hva som er teknisk mulig og hva som er etisk forsvarlig. Et tiltak kan være lovlig, men fortsatt oppleves urimelig. Et tiltak kan være nyttig for flertallet, men skade en sårbar gruppe.

Et godt svar på en drøftingsoppgave må vise at du ser konflikten mellom hensynene. Ikke skriv bare «på den ene siden» og «på den andre siden» uten å forklare hvorfor argumentene betyr noe.

## 2.2 En fast drøftingsmodell

Bruk modellen **S-I-K-A-T**:

- **S – Situasjon:** Hva skjer? Hva er teknologien og beslutningen?
- **I – Interessenter:** Hvem påvirkes direkte og indirekte?
- **K – Konflikt:** Hvilke verdier eller hensyn kolliderer?
- **A – Alternativer:** Hvilke andre løsninger eller sikkerhetstiltak finnes?
- **T – Tilråding:** Hva anbefaler du, og hvorfor?

Du kan også nevne kortsiktige og langsiktige konsekvenser, sannsynlighet, alvorlighetsgrad og hvem som bærer risikoen.

## 2.3 Personvern og personopplysninger

**Personopplysninger** er opplysninger som kan knyttes til en identifisert eller identifiserbar person. Navn og fødselsnummer er tydelige eksempler, men også lokasjonsdata, IP-adresser, bilder, bruker-ID-er og kombinasjoner av indirekte opplysninger kan identifisere noen.

**Særlige kategorier personopplysninger** omfatter blant annet opplysninger om helse, etnisk opprinnelse, politiske meninger, religion, fagforeningsmedlemskap, genetiske og biometriske data til entydig identifikasjon, seksuelle forhold og seksuell orientering. Slike opplysninger har særskilt beskyttelse.

**Behandling** omfatter blant annet innsamling, registrering, lagring, bruk, sammenstilling, utlevering og sletting.

### GDPR – grunnleggende prinsipper

Du bør kunne forklare disse prinsippene med egne ord:

1. **Lovlighet, rettferdighet og åpenhet:** Behandlingen må ha gyldig grunnlag, være rettferdig og forståelig for personen.
2. **Formålsbegrensning:** Data skal samles inn for tydelige, legitime formål og ikke brukes videre på en uforenlig måte.
3. **Dataminimering:** Ikke samle inn flere personopplysninger enn det som er nødvendig.
4. **Riktighet:** Data skal være korrekte og oppdateres ved behov.
5. **Lagringsbegrensning:** Ikke oppbevar personopplysninger lenger enn nødvendig.
6. **Integritet og konfidensialitet:** Data skal beskyttes mot uautorisert tilgang, tap, endring og lekkasje.
7. **Ansvarlighet:** Den behandlingsansvarlige må kunne dokumentere at prinsippene følges.

**Viktig:** Samtykke er ikke det eneste mulige behandlingsgrunnlaget. Andre mulige grunnlag kan være avtale, rettslig forpliktelse, vitale interesser, oppgave i allmennhetens interesse/offentlig myndighet og berettiget interesse når vilkårene er oppfylt. Hvilket grunnlag som passer, må vurderes konkret.

## 2.4 Kameraovervåking

Kameraovervåking kan forebygge eller oppklare hendelser, beskytte ansatte og kunder og gi dokumentasjon. Samtidig kan det oppleves kontrollerende, fange opp uvedkommende personer, registrere bevegelsesmønstre og endre hvordan folk oppfører seg.

Når du vurderer kameraovervåking, spør:

- Hva er det konkrete formålet?
- Er overvåking nødvendig for dette formålet?
- Finnes mindre inngripende alternativer, som bedre lys, alarm eller adgangskontroll?
- Hvor skal kameraene peke? Hvilke områder skal ikke filmes?
- Hvem har tilgang til opptakene?
- Hvor lenge lagres opptakene?
- Hvordan informeres de registrerte?
- Hvordan hindres bruk til andre formål?

**Eksempel:** Et kamera ved inngangen kan være lettere å begrunne enn kameraer i pauserom, garderober eller undervisningsrom. Behovet og inngrepet må vurderes konkret.

## 2.5 Algoritmisk skjevhet og kunstig intelligens

En algoritme er en fremgangsmåte for å løse et problem. Når algoritmer brukes til å rangere jobbsøkere, vurdere kreditt eller anbefale innhold, kan resultatet påvirke menneskers muligheter.

Algoritmisk skjevhet kan oppstå når:

- målet algoritmen optimaliserer, ikke samsvarer med det mennesker egentlig ønsker.

En KI-modell kan være svært presis i gjennomsnitt og samtidig gjøre mange feil for en bestemt gruppe. Derfor bør man undersøke resultatene per gruppe, teste systemet på representativt materiale, ha menneskelig kontroll og gjøre det mulig å klage på avgjørelser.

**Eksempel:** En automatisk søknadsmodell trenes på historiske ansettelser. Hvis virksomheten tidligere har ansatt flest personer fra én bestemt gruppe, kan systemet lære at historisk mønster er «suksess» og rangere andre kandidater lavere.

## 2.6 Opphavsrett og digital deling

Opphavsrett beskytter skapende verk, for eksempel tekst, bilder, musikk, film og programkode. At noe ligger på internett, betyr ikke at det er fritt å kopiere eller publisere. Kildehenvisning alene gir ikke automatisk rett til å bruke materialet.

## 2.7 Informasjonsteknologi og makt

Digitale plattformer kan påvirke hvilken informasjon mennesker ser, hvilke produkter de kjøper og hvilke meninger som får spredning. Anbefalingsalgoritmer kan gjøre tjenester mer relevante, men også forsterke filterbobler eller fremme innhold som skaper sterke reaksjoner.

## 2.8 Bærekraft og teknologi

Digitale løsninger kan redusere papirbruk og reiser, men har også miljøkostnader. Elektronikk krever metaller, produksjon og transport. Datasentre bruker energi og kjøling. Kort levetid på utstyr skaper elektronisk avfall.

Et bærekraftig IT-valg kan innebære å forlenge levetiden på utstyr, reparere, redusere unødvendig datalagring, velge energieffektive løsninger, designe programvare som fungerer på eldre enheter og vurdere miljøpåvirkningen i hele livsløpet.

# KAPITTEL 3 – ALGORITMISK TENKNING OG PROGRAMMERINGSGRUNNLAG

## 3.1 Hva er programmering?

Programmering er å beskrive en fremgangsmåte som en datamaskin kan utføre. Et program tar ofte imot data, behandler dem etter bestemte regler og gir et resultat.

En nyttig modell er **input – processing – output**:

- Input: brukeren skriver inn alder.
- Processing: programmet undersøker om alderen er over en grense.
- Output: programmet viser hvilken kategori brukeren tilhører.

Programmering krever at problemet brytes ned i presise trinn. Mennesker kan forstå uklare instruksjoner, men en datamaskin følger den logikken som faktisk er programmert.

## 3.2 Algoritmer

En algoritme er en endelig, tydelig beskrivelse av trinn som løser en oppgave. En algoritme bør ha:

- tydelige inputverdier,
- en definert fremgangsmåte,
- entydige instruksjoner,
- et resultat eller en stoppbetingelse,
- og helst korrekt håndtering av gyldige og ugyldige verdier.

Eksempel: Finn største tall i en liste.

1. Anta at første tall er størst.
2. Gå gjennom resten av tallene ett etter ett.
3. Hvis et tall er større enn det største du har sett, oppdater største.
4. Når listen er ferdig, returner største.

Pseudokode:

```text
FUNKSJON finn_storst(liste)
    HVIS liste er tom
        RETURNER ingen_verdi
    storst = liste[0]
    FOR hvert tall i liste
        HVIS tall > storst
            storst = tall
    RETURNER storst
```

Python:

```python
def finn_storst(liste):
    if len(liste) == 0:
        return None

    storst = liste[0]
    for tall in liste:
        if tall > storst:
            storst = tall

    return storst
```

Algoritmen gjør en sammenligning per element, omtrent proporsjonalt med antall elementer. For en liste med dobbelt så mange elementer må den omtrent gjøre dobbelt så mange sammenligninger. Dette er lineær tidsvekst, ofte skrevet O(n).

## 3.3 Variabler og datatyper

En variabel er et navn som viser til en verdi i programmet. Verdien kan endres under kjøring.

Vanlige datatyper:

- **Heltall (integer/int):** `4`, `-2`, `100`.
- **Desimaltall (float):** `3.14`, `-0.5`.
- **Tekst (string/str):** `"Hei"`, `"Oslo"`.
- **Boolsk (boolean/bool):** `True` eller `False`.
- **Liste/array:** flere verdier i en bestemt rekkefølge.
- **Dictionary/map:** verdier lagret med nøkler.

```python
navn = "Sara"        # tekst
alder = 19            # heltall
hoyde = 1.72          # desimaltall
student = True        # boolsk verdi
fag = ["IT1", "IT2"] # liste
```

Datatypen påvirker hvilke operasjoner som er meningsfulle. `19 + 1` blir 20, mens `"19" + "1"` ofte blir teksten `"191"`. Det er en vanlig feil å blande tall og tekst.

## 3.4 Operatorer

**Aritmetiske operatorer:** `+`, `-`, `*`, `/`, heltallsdivisjon (`//` i Python), modulo (`%`) og potens (`**`).

**Sammenligningsoperatorer:** `==`, `!=`, `<`, `>`, `<=`, `>=`. Resultatet er sant eller usant.

**Logiske operatorer:** `and`, `or`, `not`.

Eksempel:

```python
alder = 20
har_billett = True

if alder >= 18 and har_billett:
    print("Slipp inn")
else:
    print("Ikke adgang")
```

## 3.5 Betingelser

En betingelse lar programmet velge mellom ulike handlinger.

```python
poeng = 72

if poeng >= 80:
    karakter = "A"
elif poeng >= 60:
    karakter = "B"
else:
    karakter = "C"
```

Rekkefølgen på betingelsene betyr noe. Hvis den brede testen kommer først, kan programmet velge feil gren. I eksempelet må testen `poeng >= 80` komme før `poeng >= 60`.

## 3.6 Løkker

En løkke gjentar en kodeblokk.

**For-løkke:** Brukes ofte når du skal gå gjennom en samling eller gjenta et kjent antall ganger.

```python
for tall in [2, 4, 6]:
    print(tall)
```

**While-løkke:** Gjentar så lenge en betingelse er sann.

```python
forsok = 0
while forsok < 3:
    print("Prøv igjen")
    forsok += 1
```

Pass på uendelige løkker. Hvis betingelsen aldri blir usann, stopper ikke løkken. En teller må oppdateres eller betingelsen må på annen måte kunne endres.

## 3.7 Funksjoner

En funksjon samler kode som gjør én avgrenset oppgave. Den kan motta parametere og returnere en verdi.

```python
def beregn_mva(pris, sats=0.25):
    return pris * sats

mva = beregn_mva(200)
print(mva)  # 50.0
```

- `def` starter funksjonsdefinisjonen.
- `beregn_mva` er funksjonsnavnet.
- `pris` og `sats` er parametere.
- `sats=0.25` er en standardverdi.
- `return` sender resultatet tilbake.

Forskjellen på `print` og `return`: `print` viser noe på skjermen. `return` gir en verdi tilbake til stedet som kalte funksjonen, slik at resultatet kan brukes videre.

## 3.8 Lister og ordbøker

Lister brukes til flere verdier i rekkefølge. Indekser starter vanligvis på 0.

```python
temperaturer = [4.5, 5.0, 3.8]
print(temperaturer[0])  # 4.5
temperaturer.append(6.1)
```

Dictionary lagrer nøkkel-verdi-par:

```python
person = {
    "navn": "Ali",
    "alder": 20,
    "aktiv": True
}
print(person["navn"])
```

Bruk en liste når du trenger en ordnet samling. Bruk dictionary når du trenger å slå opp verdier via meningsfulle nøkler.

## 3.9 Pseudokode og flytskjema

Pseudokode er en språk-uavhengig beskrivelse av en algoritme. Den skal være lett å forstå, ikke nødvendigvis kjørbar.

Et flytskjema viser trinnene grafisk:

- Oval: start eller slutt.
- Rektangel: handling/prosess.
- Parallellogram: input eller output.
- Rombus: valg/betingelse.
- Piler: rekkefølge og flyt.

Eksempel – pris basert på alder:

```text
START
LES alder
HVIS alder < 18
    pris = 50
ELLERS
    pris = 100
VIS pris
SLUTT
```

Når du leser et flytskjema, følg pilene fra start. Skriv ned verdiene som endres underveis. Ikke hopp over en gren.

# KAPITTEL 4 – OBJEKTORIENTERT PROGRAMMERING (OOP)

## 4.1 Hvorfor objektorientering?

Objektorientert programmering er en måte å organisere programkode på ved å samle data og funksjonalitet i objekter. Et objekt representerer ofte noe fra virkeligheten eller en tydelig del av et system.

I stedet for å ha alle data i separate lister og alle funksjoner spredt utover programmet, samler vi relevante egenskaper og handlinger. En `Bil` kan for eksempel ha farge, merke og hastighet som attributter, og metoder for å akselerere og bremse.

OOP er nyttig når programmet har flere typer ting som har egne data og oppførsel, når strukturen blir stor nok til å trenge organisering, eller når vi ønsker å gjenbruke og utvide løsningen.

OOP er ikke alltid best. Et lite program som bare beregner gjennomsnittet av fem tall kan være enklere som én funksjon. Objektorientering skal løse et strukturproblem, ikke legges på for syns skyld.

## 4.2 Klasse og objekt

En **klasse** er en oppskrift eller mal. Et **objekt** er en konkret instans av klassen.

Klasse:

```python
class Hund:
    def __init__(self, navn, alder):
        self.navn = navn
        self.alder = alder

    def bjeff(self):
        return f"{self.navn} sier voff!"
```

Objekter:

```python
hund1 = Hund("Luna", 4)
hund2 = Hund("Max", 7)

print(hund1.bjeff())
print(hund2.navn)
```

`Hund` er klassen. `hund1` og `hund2` er forskjellige objekter. De har samme struktur, men egne verdier.

## 4.3 Attributter og metoder

- **Attributt:** Data eller egenskap som hører til objektet. For eksempel `navn`, `alder`, `saldo`.
- **Metode:** Funksjon som hører til en klasse eller et objekt. For eksempel `sett_inn_penger`, `beregn_pris`, `registrer_laan`.

Tenk på et bankkontoobjekt. Attributtene kan være kontonummer og saldo. Metodene kan være å sette inn penger, ta ut penger og vise saldo. Det er naturlig å samle saldoen og handlingene som endrer saldoen i samme klasse.

## 4.4 Konstruktør

En konstruktør brukes når et nytt objekt opprettes. I Python heter den vanligvis `__init__`. Den setter startverdiene til objektets attributter.

```python
class Konto:
    def __init__(self, eier, startbelop=0):
        self.eier = eier
        self.saldo = startbelop
```

Når vi skriver `konto = Konto("Mina", 500)`, blir konstruktøren kalt. Objektet får eier Mina og saldo 500.

En god konstruktør sørger for at objektet starter i en gyldig tilstand. For eksempel bør en konto kanskje ikke opprettes med negativ startsaldo hvis reglene ikke tillater det.

## 4.5 `self` og objektets tilstand

I Python viser `self` til objektet metoden arbeider med. Når metoden skriver `self.saldo`, endrer den saldoen til akkurat det objektet.

```python
class Konto:
    def __init__(self, saldo=0):
        self.saldo = saldo

    def sett_inn(self, belop):
        if belop > 0:
            self.saldo += belop
```

Hvis du har to kontoer, endrer `konto1.sett_inn(100)` bare `konto1`. Den andre kontoen påvirkes ikke.

## 4.6 Innkapsling

Innkapsling handler om å samle data og funksjoner og kontrollere hvordan objektets tilstand kan endres. Målet er å hindre at andre deler av programmet setter objektet i en ugyldig tilstand.

I Python brukes ofte konvensjonen `_navn` for å markere at et attributt er ment som internt. I andre språk kan man bruke `private` og `public` for tilgangskontroll.

```python
class Konto:
    def __init__(self, saldo=0):
        self._saldo = saldo

    def hent_saldo(self):
        return self._saldo

    def ta_ut(self, belop):
        if belop <= 0:
            return False
        if belop > self._saldo:
            return False
        self._saldo -= belop
        return True
```

Her kontrollerer metoden at uttaket er positivt og ikke større enn saldoen. Dette beskytter objektets regler.

## 4.7 Arv

Arv lar en klasse bygge videre på en annen klasse. Den nye klassen arver attributter og metoder fra superklassen og kan legge til eller tilpasse funksjonalitet.

Eksempel:

```python
class Dyr:
    def __init__(self, navn):
        self.navn = navn

    def lag_lyd(self):
        return "En ukjent lyd"

class Hund(Dyr):
    def lag_lyd(self):
        return "Voff"

class Katt(Dyr):
    def lag_lyd(self):
        return "Mjau"
```

`Hund` og `Katt` arver fra `Dyr`. De har felles egenskap `navn`, men ulik lyd.

Arv passer når det er et tydelig «er-en»-forhold: En hund er et dyr. En elbil er en bil. En lærer er en person.

Ikke bruk arv bare fordi to klasser har noen like attributter. Hvis forholdet egentlig er «har-en», er komposisjon ofte bedre.

## 4.8 Overstyring og polymorfisme

**Overstyring (override)** betyr at en subklasse lager sin egen versjon av en metode den arver.

**Polymorfisme** betyr at ulike objekter kan brukes gjennom et felles grensesnitt, men oppføre seg forskjellig.

```python
class Dyr:
    def lyd(self):
        return "lyd"

class Hund(Dyr):
    def lyd(self):
        return "voff"

class Katt(Dyr):
    def lyd(self):
        return "mjau"

liste = [Hund(), Katt()]
for dyr in liste:
    print(dyr.lyd())
```

Løkken trenger ikke vite nøyaktig om objektet er hund eller katt. Den vet bare at objektet har en metode `lyd`.

## 4.9 Komposisjon

Komposisjon betyr at ett objekt består av eller inneholder andre objekter. Det beskriver ofte et «har-en»-forhold.

Eksempler:
- En `Bil` har en `Motor`.
- Et `Bibliotek` har flere `Bøker`.
- En `Ordre` har flere `Ordrelinjer`.
- Et `Togsett` består av flere `Vogner`.

Komposisjon er ofte fleksibelt fordi man kan sette sammen ulike deler uten å lage et stort arvtre.

### Arv eller komposisjon?

Spør:
- Er X en type Y? Da kan arv passe.
- Består X av Y, eller bruker X Y? Da passer komposisjon ofte.

`Elbil er en Bil` kan modelleres med arv. `Bil har en Motor` modelleres med komposisjon. En motor er ikke en type bil.

## 4.10 Assosiasjoner og relasjoner

Objekter kan ha relasjoner til andre objekter. En `Student` kan være koblet til mange `Emner`. Et `Lån` kan knytte sammen ett `Medlem` og én `Bok`.

Viktige relasjoner:
- **Assosiasjon:** To klasser kjenner til eller bruker hverandre.
- **Aggregasjon:** En helhet består av deler som kan eksistere mer selvstendig.
- **Komposisjon:** En sterkere helhet-del-relasjon, der delens livsløp ofte er knyttet til helheten.
- **Arv:** En klasse spesialiserer en annen klasse.

## 4.11 Når er objektorientering et godt valg?

OOP er ofte hensiktsmessig når:
- systemet har flere tydelige entiteter med tilstand og oppførsel,
- modellen består av flere relaterte objekttyper,
- programmet skal vokse og vedlikeholdes,
- funksjonalitet kan gjenbrukes gjennom klasser og arv,
- flere utviklere trenger en forståelig struktur.

OOP kan være unødvendig komplisert når oppgaven er svært liten, når objektene ikke har meningsfull tilstand, eller når et enkelt funksjonsbasert design er mer oversiktlig.

### Gjennomarbeidet eksempel: Bibliotek

Klasser:
- `Bok`: tittel, forfatter, ISBN, tilgjengelig.
- `Medlem`: navn, medlemsnummer.
- `Lån`: bok, medlem, lånedato, frist, innlevert.
- `Bibliotek`: samling av bøker og medlemmer; metoder for å registrere utlån og innlevering.

Mulig metode i `Bok`:

```python
class Bok:
    def __init__(self, tittel, forfatter, isbn):
        self.tittel = tittel
        self.forfatter = forfatter
        self.isbn = isbn
        self.tilgjengelig = True

    def marker_utlant(self):
        if not self.tilgjengelig:
            return False
        self.tilgjengelig = False
        return True

    def marker_innlevert(self):
        self.tilgjengelig = True
```

Mulig metode i `Lån` kan registrere hvem som lånte hvilken bok og når. `Bibliotek` bør kontrollere at medlemmet finnes, at boken er tilgjengelig, og at det ikke opprettes et ugyldig lån.

# KAPITTEL 5 – OBJEKTORIENTERT MODELLERING OG UML

## 5.1 Hvorfor modellere før programmering?

En modell er en forenklet beskrivelse av et system. Den viser de delene som er viktige for problemstillingen, og utelater detaljer som ikke er nødvendige akkurat nå. Når du modellerer, prøver du å forstå hvilke objekter systemet trenger, hvilke data de må ha, hva de skal kunne gjøre, og hvordan de henger sammen.

Modellering kan gjøres før koding for å oppdage problemer tidlig. Det er lettere å endre et klassediagram enn å endre et stort program med mange avhengigheter. En modell gir også et felles språk for utviklere, brukere og oppdragsgiver.

Det finnes ikke én eneste korrekt modell for alle oppgaver. En god modell er tilpasset formålet. Hvis oppgaven handler om å låne bøker, er bok, medlem og lån sentrale begreper. Hvis oppgaven handler om bibliotekets økonomi, kan betaling, gebyr og regnskap bli viktigere.

## 5.2 UML og klassediagram

UML står for Unified Modeling Language. UML er et standardisert modelleringsspråk som kan brukes til å beskrive struktur og oppførsel i systemer. Et klassediagram viser særlig den statiske strukturen: klasser, attributter, metoder og relasjoner.

En klasse tegnes vanligvis som en boks delt i tre:

1. Klassenavn øverst.
2. Attributter i midten.
3. Metoder nederst.

Eksempel skrevet tekstlig:

```text
+---------------------------+
|          Bok              |
+---------------------------+
| - tittel: String          |
| - forfatter: String       |
| - tilgjengelig: Boolean   |
+---------------------------+
| + lånUt(): Boolean        |
| + leverInn(): void        |
| + hentTittel(): String    |
+---------------------------+
```

Synlighetssymboler:
- `+` betyr offentlig (public).
- `-` betyr privat (private).
- `#` betyr beskyttet (protected) i språk som bruker denne inndelingen.

UML er ikke kode. Diagrammet beskriver strukturen på et høyere nivå. Du kan oversette modellen til flere programmeringsspråk.

## 5.3 Relasjoner og multiplisitet

Relasjonene i et klassediagram viser hvordan objekter henger sammen.

**Assosiasjon:** En generell forbindelse mellom klasser. Eksempel: `Medlem` kan ha `Lån`.

**Arv/generaliserering:** En underklasse er en spesialisering av en overordnet klasse. Tegnes ofte med en linje og en åpen trekant som peker mot superklassen.

**Komposisjon:** En sterk helhet-del-relasjon. En `Ordre` består av `Ordrelinjer`. Hvis ordren slettes, gir det ofte mening at ordrelinjene i akkurat den ordren også forsvinner.

**Aggregasjon:** En løsere helhet-del-relasjon der delene kan eksistere separat. Bruken av aggregasjon varierer noe mellom modelleringsstiler.

**Multiplisitet** angir hvor mange objekter som kan inngå i relasjonen:
- `1`: nøyaktig én.
- `0..1`: ingen eller én.
- `*` eller `0..*`: null eller mange.
- `1..*`: minst én.
- `2..5`: fra to til fem.

Eksempel: Én `Kunde` kan ha null eller mange `Ordre`. Hver `Ordre` tilhører nøyaktig én `Kunde`.

## 5.4 Fra tekst til klassediagram – metode

Når du får en tekstlig oppgave, gjør dette:

1. Les oppgaven og marker substantiver. De kan være kandidater til klasser eller attributter.
2. Marker verb. De kan være kandidater til metoder eller relasjoner.
3. Spør hvilke begreper som må ha egen identitet og flere egenskaper. Disse blir ofte klasser.
4. Skill mellom klasser og attributter. `navn` er normalt et attributt, ikke en egen klasse. `Adresse` kan være egen klasse hvis den har flere felt eller brukes flere steder.
5. Finn relasjoner: Hvem har hvem? Hvem bruker hvem? Hvilken type er en annen?
6. Legg inn multiplisitet.
7. Se etter dobbeltlagring. Samme informasjon skal normalt ikke ligge unødvendig flere steder.
8. Kontroller at modellen støtter oppgavene systemet faktisk skal løse.

### Eksempel: Treningssenter

Oppgavebeskrivelse: Et treningssenter har medlemmer. Medlemmer kan kjøpe medlemskap. Hvert medlemskap har startdato, sluttdato og pris. Medlemmer kan booke gruppetimer. En gruppetime har tidspunkt, instruktør og maks antall plasser.

Mulige klasser:
- `Medlem`: medlemsnummer, navn, e-post.
- `Medlemskap`: startdato, sluttdato, pris, aktiv.
- `Gruppetime`: tidspunkt, maksPlasser.
- `Instruktør`: navn, kompetanse.
- `Booking`: tidspunktForBooking, status.

Relasjoner:
- Ett medlem kan ha flere medlemskap over tid, men kanskje bare ett aktivt om gangen.
- Én instruktør kan holde mange gruppetimer.
- Én gruppetime kan ha mange bookinger.
- Én booking knytter ett medlem til én gruppetime.

Det er nyttig å modellere `Booking` som egen klasse fordi koblingen mellom medlem og gruppetime har egne data, som tidspunkt og status. Hvis man bare tegner en direkte mange-til-mange-relasjon, mister man disse opplysningene.

## 5.5 Vanlige modellfeil

- Alt legges i én stor klasse.
- Man lager en klasse for hvert ord i oppgaveteksten, også ord som bare er enkle attributter.
- Arv brukes der komposisjon passer bedre.
- Relasjoner mangler multiplisitet.
- Klassene har data, men ingen meningsfulle metoder.
- Samme data lagres i flere klasser uten grunn.
- Diagrammet modellerer tekniske detaljer, men ikke oppgavens behov.

# KAPITTEL 6 – PROGRAMDESIGN, ARKITEKTUR OG ALTERNATIVE LØSNINGER

## 6.1 Hva er programdesign?

Programdesign er planleggingen av hvordan et program skal bygges opp før og under implementeringen. Du bestemmer hvordan problemet skal deles i mindre deler, hvilke data som trengs, hvordan komponentene skal samarbeide, og hvordan brukeren skal samhandle med løsningen.

Et godt design gjør løsningen lettere å forstå, teste, endre og utvide. Et dårlig design kan virke i starten, men bli vanskelig å vedlikeholde når flere krav kommer til.

## 6.2 Krav: funksjonelle og ikke-funksjonelle

**Funksjonelle krav** beskriver hva systemet skal gjøre:
- Brukeren skal kunne registrere en bok.
- Systemet skal kunne registrere utlån.
- Systemet skal vise hvilke bøker som er tilgjengelige.

**Ikke-funksjonelle krav** beskriver kvalitet eller rammer:
- Systemet skal være enkelt å bruke.
- Personopplysninger skal beskyttes.
- Svar skal komme innen to sekunder under normal belastning.
- Systemet skal fungere på mobil og PC.
- Systemet skal kunne sikkerhetskopieres.

Kravene bør være konkrete nok til å testes. «Programmet skal være raskt» er uklart. «Søk etter en bok skal normalt gi resultat innen to sekunder ved 10 000 registrerte bøker» kan testes.

## 6.3 Modularitet og lagdeling

Modularitet betyr å dele et program i mindre deler med tydelig ansvar. En modul eller klasse bør ha en avgrenset oppgave.

Eksempel på lagdeling i en enkel applikasjon:

1. **Presentasjonslag:** Viser informasjon og tar imot brukerhandlinger.
2. **Logikklag:** Utfører regler, beregninger og validering.
3. **Datalag:** Leser og skriver data til fil eller database.

Fordelen er at en endring i brukergrensesnittet ikke nødvendigvis krever at databasekoden endres. Det er lettere å teste logikken separat.

## 6.4 Prosedyreorientert, funksjonsorientert og objektorientert design

**Prosedyreorientert løsning:** Programmet organiseres rundt trinn og prosedyrer. Dette kan passe for små, lineære oppgaver.

**Funksjonsorientert løsning:** Oppgaver samles i funksjoner som mottar data og returnerer resultat. Dette kan gi enkel gjenbruk og testing.

**Objektorientert løsning:** Data og handlinger organiseres i klasser og objekter. Dette passer når systemet består av relaterte objekter med tilstand og oppførsel.

Ingen av modellene er automatisk best. Velg ut fra problemets struktur og behov.

## 6.5 Algoritmevalg og effektivitet

To algoritmer kan løse samme oppgave, men bruke ulik mengde tid eller minne.

- Lineært søk går gjennom elementene én etter én. Det fungerer også når listen ikke er sortert. Tidsbruk øker omtrent lineært med antall elementer: O(n).
- Binærsøk halverer søkeområdet for hvert steg, men krever at dataene er sortert. Tidsbruk øker omtrent logaritmisk: O(log n).
- Enkel boblesortering er lett å forstå, men kan bruke omtrent kvadratisk antall sammenligninger: O(n²).

Du trenger ikke alltid kunne bevise kompleksitet matematisk, men bør forstå at en løsning som fungerer for 10 elementer, kan bli treg for 1 million.

## 6.6 Sammenlign alternativer systematisk

Når du får spørsmålet «hvilken løsning ville du valgt?», vurder:
- korrekthet,
- lesbarhet,
- vedlikehold,
- testbarhet,
- ytelse,
- sikkerhet,
- brukervennlighet,
- utviklingstid og kompleksitet,
- mulighet for videreutvikling.

### Eksempel: Lagre en handleliste

**Alternativ A – CSV:** Godt for en enkel tabell med rader og kolonner. Lett å åpne i regneark. Mindre egnet for nestede strukturer og kompliserte relasjoner.

**Alternativ B – JSON:** Godt for hierarkiske data og utveksling mellom applikasjoner. Kan inneholde lister og objekter. Krever at programmet håndterer struktur og validering.

**Alternativ C – database:** Godt når mange brukere skal oppdatere data, data har relasjoner, og søk/oppdatering må være pålitelig. Mer oppsett og kompleksitet.

For en personlig liste med få elementer kan CSV eller JSON være tilstrekkelig. For en nettbutikk med kunder, ordre og varer vil en database normalt passe bedre.

# KAPITTEL 7 – TESTING, FEILSØKING OG KVALITETSSIKRING

## 7.1 Hvorfor teste?

Et program som kjører uten å krasje, er ikke nødvendigvis korrekt. Programmet kan gi feil resultat, håndtere spesialtilfeller dårlig eller være vanskelig å bruke. Testing undersøker om løsningen oppfører seg som forventet.

Testing kan avdekke feil, men kan ikke bevise at programmet er feilfritt i alle situasjoner. Derfor må vi velge testtilfeller som gir god dekning av funksjoner, grenseverdier og risikoer.

## 7.2 Tre hovedtyper feil

**Syntaksfeil:** Koden bryter reglene i programmeringsspråket. Eksempel: manglende kolon i Python eller feil parentes.

**Kjøretidsfeil:** Programmet starter, men feiler under kjøring. Eksempel: dele på null, åpne en fil som ikke finnes, eller hente en listeindeks som er utenfor grensene.

**Logisk feil:** Programmet kjører, men gir feil resultat. Eksempel: rabatt trekkes fra to ganger eller betingelsen bruker `>` i stedet for `>=`.

En logisk feil kan være vanskeligst å oppdage fordi programmet ikke nødvendigvis viser en feilmelding.

## 7.3 Systematisk feilsøking

En god feilsøkingsprosess:

1. Gjenskap feilen med samme input og samme fremgangsmåte.
2. Skriv ned hva du forventet og hva som faktisk skjedde.
3. Finn det minste eksempelet som fortsatt utløser feilen.
4. Les feilmeldingen og finn relevant linje.
5. Bruk utskrift, logger eller debugger til å undersøke verdier.
6. Formuler en hypotese om årsaken.
7. Endre én ting om gangen.
8. Kjør testen på nytt.
9. Kjør relevante regresjonstester for å kontrollere at andre ting fortsatt fungerer.

Ikke endre fem ting samtidig. Da blir det vanskelig å vite hvilken endring som faktisk løste problemet.

## 7.4 Testnivåer

- **Enhetstest:** Tester en liten del, for eksempel én funksjon eller metode.
- **Integrasjonstest:** Tester om flere deler fungerer sammen, for eksempel programlogikk og database.
- **Systemtest:** Tester hele systemet som én helhet.
- **Akseptansetest:** Undersøker om løsningen dekker brukerens behov og krav.

## 7.5 Testteknikker

**Normalverdier:** Test vanlige, forventede inputverdier.

**Grenseverdier:** Test rett under, på og rett over grenser. Hvis en person må være minst 18 år, test 17, 18 og 19.

**Ugyldig input:** Tom tekst, negative tall, feil datoformat, bokstaver der det forventes tall.

**Ekvivalensklasser:** Del input i grupper som forventes å oppføre seg likt. For billettpris kan gruppene være barn, ungdom, voksen og ugyldig alder.

**Tilstandsoverganger:** Test ulike sekvenser av handlinger. En bok kan være tilgjengelig, utlånt og innlevert. Test at overgangen mellom tilstandene er gyldig.

**Regresjonstest:** Kjør tidligere tester etter en endring for å sikre at gammel funksjonalitet fortsatt virker.

## 7.6 Testplan

En testplan bør inneholde:
- Hva som testes.
- Testdata/input.
- Forventet resultat.
- Faktisk resultat.
- Bestått/ikke bestått.
- Eventuell kommentar eller feilrapport.

Eksempel – funksjonen `billettpris(alder)`:

| Test | Input | Forventet resultat | Hvorfor |
|---|---:|---:|---|
| T1 | -1 | Ugyldig | Negativ alder |
| T2 | 0 | 80 | Nedre gyldige grense |
| T3 | 11 | 80 | Siste barn-alder |
| T4 | 12 | 100 | Første ungdomsalder |
| T5 | 17 | 100 | Siste ungdomsalder |
| T6 | 18 | 140 | Første voksenalder |

## 7.7 Debugger og logging

En debugger lar utvikleren stoppe programmet på bestemte steder, se variabelverdier og gå gjennom koden steg for steg. Et breakpoint er et stoppunkt.

Logging skriver hendelser til en logg. I stedet for å skrive alt til skjermen kan programmet registrere tidspunkt, nivå og melding. Logg bør ikke inneholde unødvendige personopplysninger eller hemmeligheter som passord.

## 7.8 Testbar kode

Kode er lettere å teste når funksjoner har tydelige oppgaver, input og output. Hvis en funksjon både leser fra fil, oppdaterer database, viser brukergrensesnitt og sender e-post, blir det vanskelig å teste hver del separat.

Ved å skille logikk fra input/output kan du teste beregningene uten å starte hele systemet.

# KAPITTEL 8 – GJENBRUKBAR PROGRAMKODE OG KODEKVALITET

## 8.1 Hva betyr gjenbrukbar kode?

Gjenbrukbar kode er kode som kan brukes i flere situasjoner uten å kopieres og endres manuelt hver gang. Det kan være en funksjon, metode, klasse, modul eller et bibliotek.

Hvis samme beregning står kopiert på fem steder, må alle fem oppdateres når reglene endres. Hvis beregningen ligger i én funksjon, kan alle deler av programmet bruke samme funksjon.

## 8.2 Funksjoner som abstraksjon

Abstraksjon betyr å skjule unødvendige detaljer bak et enkelt grensesnitt. Brukeren av en funksjon trenger ikke vite alle trinnene i implementeringen; det holder å vite hva funksjonen gjør, hva den tar imot og hva den returnerer.

```python
def beregn_totalpris(priser):
    return sum(priser)
```

Koden som kaller funksjonen trenger ikke vite hvordan `sum` fungerer internt. Den trenger bare en liste med priser.

## 8.3 Parametere og returverdier

Parametere gjør funksjoner fleksible. I stedet for å skrive én funksjon for hver pris, kan du sende inn prisen som parameter.

En returverdi lar funksjonen gi resultatet tilbake. Det gjør den enklere å kombinere med annen kode og enklere å teste.

## 8.4 DRY og KISS

- **DRY – Don't Repeat Yourself:** Unngå unødvendig duplisering av regler og kode.
- **KISS – Keep It Simple:** Velg en enkel løsning som dekker behovet, framfor unødvendig kompleksitet.

Dette betyr ikke at all gjentakelse er feil. To kodeblokker kan se like ut, men gjøre forskjellige ting. Du bør bare lage en felles funksjon når det faktisk gjør programmet tydeligere og tryggere.

## 8.5 Modularitet

En modul er en avgrenset del av programmet. Et godt moduldesign gjør at deler kan utvikles og testes uavhengig.

Eksempel på moduler i en nettbutikk:
- `produkter`: produktinformasjon og søk.
- `handlekurv`: legge til og fjerne varer.
- `betaling`: betaling og kvittering.
- `brukere`: registrering og innlogging.

Moduler bør kommunisere gjennom tydelige grensesnitt og ikke være unødvendig avhengige av interne detaljer i hverandre.

## 8.6 Dokumentasjon og navngiving

Gode navn forklarer hensikten: `beregn_totalpris` er bedre enn `f1`. Kommentarer bør forklare hvorfor koden gjør noe uvanlig, ikke bare gjenta selve kodelinjen.

Docstrings eller funksjonsbeskrivelser bør forklare:
- formålet,
- parametere,
- returverdi,
- forventninger og begrensninger.

2. Hvorfor er det bedre å bruke en parameter enn å hardkode samme verdi i flere funksjoner?

# KAPITTEL 9 – BRUKERVENNLIGHET, UX OG UNIVERSELL UTFORMING

## 9.1 Hva er brukervennlighet?

Brukervennlighet handler om hvor enkelt og effektivt en bestemt brukergruppe kan nå målene sine med et system. Et program kan ha mange funksjoner, men fortsatt være vanskelig å bruke.

Viktige dimensjoner:
- **Lærbarhet:** Hvor raskt forstår en ny bruker hvordan systemet fungerer?
- **Effektivitet:** Hvor raskt kan en erfaren bruker utføre oppgaven?
- **Hukommelsesvennlighet:** Må brukeren huske kompliserte steg fra tidligere?
- **Feiltoleranse:** Hvor lett er det å gjøre feil, og hvor lett er det å rette dem?
- **Tilfredshet:** Oppleves systemet som forståelig og behagelig?

## 9.2 Brukerbehov og målgrupper

Før du designer et system, må du vite hvem som skal bruke det og i hvilken situasjon. En app for barn, en intern løsning for ansatte og et offentlig skjema har ulike behov.

Spør:
- Hvem er brukerne?
- Hva prøver de å få gjort?
- Hvor ofte bruker de systemet?
- Hvilke digitale ferdigheter har de?
- Har de behov for hjelpemidler eller alternative måter å navigere på?
- Hvilke feil kan få alvorlige konsekvenser?

En løsning som er lett for utvikleren, er ikke nødvendigvis lett for brukeren.

## 9.3 Brukergrensesnitt og tilbakemelding

Et brukergrensesnitt bør gi tydelig tilbakemelding. Når brukeren trykker «Lagre», bør systemet vise om lagringen lyktes. Hvis noe går galt, bør feilmeldingen forklare hva brukeren kan gjøre.

Gode prinsipper:
- konsekvent plassering og utforming av knapper,
- tydelige etiketter,
- forståelig språk,
- god kontrast,
- synlig fokus når man navigerer med tastatur,
- bekreftelse før destruktive handlinger,
- gode standardvalg,
- mulighet til å angre når det er hensiktsmessig.

## 9.4 Affordance, signifiers og mental modell

**Affordance** handler om hvilke handlinger et objekt eller grensesnitt muliggjør. En knapp kan trykkes, en tekstboks kan få tekst.

**Signifier** er et synlig tegn som viser hva som kan gjøres, for eksempel en knapp med teksten «Last opp fil».

**Mental modell** er brukerens forståelse av hvordan systemet fungerer. Hvis en handlekurv viser varer, forventer brukeren at varene blir med videre til betaling. Hvis systemet oppfører seg annerledes, skaper det forvirring.

## 9.5 Universell utforming og tilgjengelighet

Universell utforming innebærer å utforme produkter og tjenester slik at de kan brukes av flest mulig, også personer med funksjonsnedsettelser. Digitale tjenester bør blant annet støtte tastaturnavigasjon, ha god kontrast, bruke forståelige overskrifter, gi tekstalternativer til bilder og ikke formidle informasjon bare gjennom farge.

Viktige forhold:
- Tekst må kunne leses og forstørres.
- Kontrast må gjøre tekst synlig.
- Knapper og lenker må være tydelig navngitt.
- Bilder som formidler informasjon, bør ha alternativ tekst.
- Video med tale bør ha teksting.
- Skjema må ha tydelige etiketter og forståelige feilmeldinger.
- Brukeren bør kunne navigere med tastatur og hjelpemidler.

## 9.6 Brukertesting

La faktiske brukere løse realistiske oppgaver mens du observerer. Ikke fortell dem hvert klikk. Legg merke til hvor de nøler, hva de misforstår og hvor feil oppstår.

Eksempel på testoppgave: «Finn neste ledige time på tirsdag og avbestill bookingen.» Ikke spør bare om brukeren liker fargene. Undersøk om brukeren faktisk klarer å utføre handlingen.

Du kan måle:
- om oppgaven blir løst,
- hvor lang tid den tar,
- hvor mange feil som oppstår,
- hvor ofte brukeren trenger hjelp,
- hvordan brukeren opplever løsningen.

# KAPITTEL 10 – SYSTEMUTVIKLING, PROSJEKTARBEID OG SAMARBEIDSVERKTØY

## 10.1 Systemutvikling

Systemutvikling er prosessen med å planlegge, designe, utvikle, teste, innføre og vedlikeholde et informasjonssystem. En vanlig arbeidsflyt er:

1. Behovs- og problemforståelse.
2. Kravspesifikasjon.
3. Design og modellering.
4. Implementering.
5. Testing.
6. Levering og innføring.
7. Vedlikehold og videreutvikling.

I praksis kan fasene overlappe og gjentas. Når vi tester en prototype, kan vi oppdage at vi misforsto et brukerbehov og må gå tilbake til designfasen.

## 10.2 Fossefallsmodell

Fossefallsmodellen deler utviklingen inn i faser som i hovedsak gjennomføres i rekkefølge. Den kan passe når kravene er tydelige og stabile, og når dokumentasjon og formell godkjenning er viktig.

Fordeler:
- tydelige faser og leveranser,
- enkel planlegging,
- dokumentasjon av beslutninger.

Ulemper:
- endringer sent i prosjektet kan bli dyre,
- brukerne ser ofte løsningen sent,
- misforståtte krav kan oppdages sent.

## 10.3 Smidig utvikling

Smidig utvikling deler arbeidet i mindre leveranser og bruker hyppige tilbakemeldinger. Teamet prøver ut, vurderer og justerer løsningen underveis.

Fordeler:
- raskere tilbakemelding,
- lettere å prioritere etter faktisk behov,
- endringer kan tas inn fortløpende.

Ulemper:
- krever god kommunikasjon,
- kan gi svakere forutsigbarhet hvis mål og prioriteringer stadig endres,
- dokumentasjon kan bli forsømt hvis teamet ikke har gode rutiner.

## 10.4 Scrum – grunnbegreper

Scrum er et rammeverk for smidig arbeid.

- **Product Owner:** Prioriterer produktets behov og produktkø.
- **Scrum Master:** Hjelper teamet med å følge Scrum og fjerne hindringer.
- **Developers/utviklingsteam:** Lager produktet.
- **Product Backlog:** Prioritert liste over arbeid som kan være nødvendig.
- **Sprint:** Tidsavgrenset arbeidsperiode.
- **Sprint Planning:** Planlegger hva teamet skal gjøre i sprinten.
- **Daily Scrum:** Kort daglig møte for å koordinere arbeidet.
- **Sprint Review:** Viser og vurderer resultatet med interessenter.
- **Retrospective:** Teamet vurderer hvordan samarbeidet kan forbedres.

Scrum er ikke bare å ha daglige møter. Det handler om synlig arbeid, prioritering, korte leveransesykluser og kontinuerlig forbedring.

## 10.5 Versjonskontroll og Git

Versjonskontroll holder oversikt over endringer i filer over tid. Git gjør det mulig å lagre versjoner, opprette grener, slå sammen arbeid og gå tilbake hvis noe går galt.

- **Repository (repo):** Prosjektets versjonsstyrte område.
- **Commit:** Et lagret sett med endringer og en beskrivelse.
- **Branch:** En separat utviklingslinje.
- **Merge:** Slå sammen endringer fra ulike grener.
- **Pull:** Hente endringer fra et eksternt repo.
- **Push:** Sende egne commits til et eksternt repo.
- **Merge conflict:** Når Git ikke kan slå sammen endringer automatisk.

Eksempel på enkel arbeidsflyt:

1. Hent siste versjon.
2. Opprett en egen branch for en funksjon.
3. Gjør små, logiske endringer.
4. Test.
5. Lag commit med tydelig melding.
6. Del branchen eller slå den sammen etter gjennomgang.

Git er ikke en sikkerhetskopi alene. Eksterne repositories kan hjelpe, men det er fortsatt viktig å ha rutiner for backup og tilgangskontroll.

## 10.6 Samarbeid og dokumentasjon

Et team bør avtale navngiving, kodeformat, arbeidsfordeling, hvordan feil rapporteres, hvordan endringer gjennomgås og hvordan beslutninger dokumenteres.

Dokumentasjon kan bestå av:
- krav og brukerhistorier,
- klassediagrammer og arkitektur,
- README med oppstartsinstruksjoner,

- testplan og testresultater,

# KAPITTEL 11 – DATAREPRESENTASJON, FILFORMATER OG STANDARDER

## 11.1 Hva er datarepresentasjon?

Datamaskiner behandler informasjon som bitmønstre. En bit har verdien 0 eller 1. Åtte bit er én byte. Flere byte kan representere tall, tekst, bilder, lyd eller instruksjoner.

Data må ha en avtalt tolkning. Det samme bitmønsteret kan bety ulike ting dersom systemene bruker forskjellige datatyper eller tegnkodinger.

## 11.2 Binært og heksadesimalt

Binært tallsystem bruker bare 0 og 1. Hver posisjon representerer en toerpotens.

Eksempel: `1011₂` betyr:

`1×8 + 0×4 + 1×2 + 1×1 = 11₁₀`.

Heksadesimalt tallsystem bruker sifrene 0–9 og bokstavene A–F. Ett heksadesimalt siffer representerer fire bit. Heksadesimal er kompakt og brukes ofte til farger, minneadresser og byteverdier.

Du bør forstå hvorfor digitale systemer bruker binære verdier, og kunne forklare at tekst, bilder og lyd må kodes som tallverdier.

## 11.3 Tegnkoding og Unicode

Tegn må representeres med tall. ASCII er en eldre tegnstandard som dekker et begrenset tegnsett. Unicode gir kodepunkter for et stort utvalg av tegn fra ulike språk og symboler. UTF-8 er en vanlig måte å kode Unicode-tegn på.

Hvis to systemer bruker ulik tegnkoding, kan tekst bli vist feil. Å bruke UTF-8 konsekvent er derfor viktig ved lagring og utveksling av tekst.

## 11.4 CSV

CSV (Comma-Separated Values) er et tekstformat for tabellformede data. Hver linje representerer ofte en rad, og feltene skilles med komma eller et annet avtalt skilletegn.

```csv
navn,alder,by
Sara,19,Oslo
Ali,21,Drammen
Mina,18,Bergen
```

Fordeler:
- enkelt og lesbart,
- lett å åpne i regneark,
- passer til enkle tabeller,
- støttes av mange programmer.

Ulemper:
- datatyper er ikke alltid tydelig definert,
- relasjoner mellom tabeller må håndteres separat,
- komma, semikolon, sitattegn og linjeskift kan skape problemer,
- ikke egnet for kompliserte hierarkier.

CSV bør leses med et CSV-bibliotek, ikke alltid ved å splitte tekst manuelt, fordi verdier kan inneholde skilletegn i anførselstegn.

## 11.5 JSON

JSON (JavaScript Object Notation) er et tekstformat for strukturerte data. Det bruker objekter med nøkkel-verdi-par og lister.

```json
{
  "navn": "Sara",
  "alder": 19,
  "fag": ["IT1", "IT2"],
  "aktiv": true
}
```

Fordeler:
- lett å lese for mennesker,
- støtter lister og nestede objekter,
- vanlig i web-API-er,
- lett å bruke på tvers av programmeringsspråk.

Ulemper:
- strukturen må være kjent og valideres,
- større eller kompliserte data kan bli tunge å behandle,
- JSON definerer ikke i seg selv regler for hvem som får lese eller endre data.

## 11.6 XML

XML er et markeringsformat med tagger. Det brukes blant annet i eldre systemer, dokumentformater og enkelte integrasjoner.

```xml
<person>
  <navn>Sara</navn>
  <alder>19</alder>
</person>
```

XML er mer verbost enn JSON, men har muligheter for skjema og validering. Du trenger først og fremst å forstå hva formatet er, og at systemer må være enige om struktur og betydning.

## 11.7 Velge format

- CSV: enkel tabellutveksling.
- JSON: strukturerte objekter/lister og webkommunikasjon.
- XML: strukturerte dokumenter og enkelte systemintegrasjoner.
- Relasjonsdatabase: større datamengder med relasjoner, oppdateringer og spørringer.

Valg avhenger av datatypene, kompleksiteten, hvem som skal bruke dataene, hvor ofte de endres og hvilke integrasjoner som kreves.

# KAPITTEL 12 – DATABASER OG SQL

## 12.1 Hva er en database?

En database er en organisert samling data som kan lagres, søkes i og oppdateres. Et databasehåndteringssystem (DBMS) administrerer tilgangen til dataene og hjelper med integritet, spørringer, transaksjoner og sikkerhet.

En relasjonsdatabase organiserer data i tabeller. Hver tabell beskriver en type entitet eller relasjon.

## 12.2 Tabeller, rader og kolonner

- Tabell: samling av samme type registreringer.
- Rad/post: én registrering.
- Kolonne/felt: én egenskap.

Eksempel `Kunde`:

| kunde_id | navn | epost |
|---:|---|---|
| 1 | Sara | sara@example.no |
| 2 | Ali | ali@example.no |

## 12.3 Primærnøkkel og fremmednøkkel

**Primærnøkkel (primary key)** identifiserer hver rad unikt. `kunde_id` kan være primærnøkkel.

**Fremmednøkkel (foreign key)** peker på en rad i en annen tabell. En ordre kan ha `kunde_id` som fremmednøkkel for å vise hvem som eier ordren.

Dette gjør at vi ikke trenger å skrive kundens navn og e-post inn i hver ordre. Vi kan hente opplysningene gjennom relasjonen.

## 12.4 Relasjoner

- Én-til-én: én rad kobles til maksimalt én rad i en annen tabell.
- Én-til-mange: én kunde kan ha mange ordre.
- Mange-til-mange: flere elever kan ha flere fag. Dette løses vanligvis med en koblingstabell, for eksempel `ElevFag`.

## 12.5 SQL – grunnleggende spørringer

SQL er et språk for å definere og arbeide med relasjonsdatabaser.

```sql
SELECT navn, epost
FROM Kunde
WHERE kunde_id = 1;
```

`SELECT` velger kolonner, `FROM` angir tabell, `WHERE` filtrerer rader.

Legge til data:

```sql
INSERT INTO Kunde (navn, epost)
VALUES ('Sara', 'sara@example.no');
```

Oppdatere data:

```sql
UPDATE Kunde
SET epost = 'ny@example.no'
WHERE kunde_id = 1;
```

Slette data:

```sql
DELETE FROM Kunde
WHERE kunde_id = 1;
```

**Viktig:** `UPDATE` eller `DELETE` uten riktig `WHERE` kan endre eller slette alle rader i tabellen. Derfor må man kontrollere spørringer og ta backup.

## 12.6 JOIN

JOIN brukes for å kombinere data fra relaterte tabeller.

```sql
SELECT Kunde.navn, Ordre.ordre_dato
FROM Kunde
JOIN Ordre ON Kunde.kunde_id = Ordre.kunde_id;
```

Her kobles hver ordre til kunden som har lagt inn ordren.

## 12.7 Normalisering

Normalisering er en måte å organisere tabeller på for å redusere unødvendig duplisering og oppdateringsfeil.

Hvis kundens adresse gjentas i 500 ordre, kan det oppstå inkonsistens dersom kunden flytter. Ved å lagre kundeinformasjon i kundetabellen og bruke fremmednøkkel fra ordre, trenger adressen bare å oppdateres ett sted.

Du trenger ikke nødvendigvis kunne alle normalformer i dybden, men bør forstå hvorfor tabeller deles opp og hvordan relasjoner hindrer duplisering.

## 12.8 Transaksjoner og dataintegritet

En transaksjon er en samling databaseoperasjoner som behandles som én logisk enhet. Ved bankoverføring må penger trekkes fra én konto og legges til en annen. Hvis bare den ene operasjonen fullføres, blir dataene feil.

ACID er fire egenskaper som ofte beskriver transaksjonssikkerhet:
- Atomicity: alt eller ingenting.
- Consistency: dataene følger regler før og etter.
- Isolation: samtidige transaksjoner påvirker ikke hverandre på en uforutsigbar måte.
- Durability: bekreftede endringer blir bevart.

# KAPITTEL 13 – REELLE DATASETT: INNHENTING, RENSING, ANALYSE OG PRESENTASJON

## 13.1 Hva er et datasett?

Et datasett er en samling registrerte observasjoner. Det kan være temperaturmålinger, trafikkdata, salg, strømforbruk, befolkningsstatistikk, treningsresultater eller målinger fra sensorer.

En rad representerer ofte én observasjon. Kolonnene beskriver egenskapene ved observasjonen. Et godt datasett har tydelig dokumentasjon av hva kolonnene betyr, hvilke enheter som brukes, hvor og når dataene er samlet inn, og eventuelle begrensninger.

Eksempel:

| dato | sted | temperatur_c | nedbor_mm |
|---|---|---:|---:|
| 2026-11-01 | Oslo | 6.2 | 0.0 |
| 2026-11-02 | Oslo | 4.8 | 2.4 |
| 2026-11-03 | Oslo | 5.1 | 0.8 |

## 13.2 Innhenting av data

Data kan hentes fra:
- CSV- eller JSON-filer,
- databaser,
- offentlige åpne data,
- sensorer,
- API-er,
- spørreundersøkelser,
- manuelle registreringer.

Når du henter data, bør du vurdere kilde, formål, tillatelser, datakvalitet og personvern. Ikke alle data som kan lastes ned, kan brukes fritt til alle formål.

## 13.3 Datakvalitet

Før analyse bør du undersøke:

- **Manglende verdier:** Tomme felt, `NULL`, `NaN`.
- **Duplikater:** Samme observasjon registrert flere ganger.
- **Feil format:** Dato som tekst, desimalkomma, blandede enheter.
- **Ugyldige verdier:** Temperatur på 900 °C i et datasett for vanlig vær.
- **Avvikere:** Svært høye eller lave verdier som kan være feil eller reelle spesialtilfeller.
- **Skjev utvalg:** Datasettet representerer ikke hele gruppen du vil si noe om.
- **Manglende kontekst:** Uklart hva en kolonne betyr eller når data ble målt.

Ikke fjern en avviker automatisk. En ekstrem verdi kan være en feil, men den kan også være den viktigste observasjonen. Undersøk årsaken før du bestemmer deg.

## 13.4 Rensing og klargjøring

En ryddig arbeidsflyt:

1. Les datasettet.
2. Undersøk antall rader og kolonner.
3. Se på noen rader.
4. Kontroller datatyper.
5. Sjekk manglende verdier og duplikater.
6. Kontroller verdiområder og enheter.
7. Rydd eller marker problemer.
8. Dokumenter hvilke endringer som ble gjort.
9. Lagre en bearbeidet versjon uten å overskrive originalen.

Det er viktig å bevare originaldata slik at analysen kan etterprøves.

## 13.5 Statistiske mål

**Antall (n):** Hvor mange observasjoner det finnes.

**Sum:** Summen av alle verdiene.

**Gjennomsnitt:** Summen delt på antall observasjoner. Følsomt for ekstreme verdier.

**Median:** Midterste verdi når data sorteres. Mindre påvirket av ekstreme verdier.

**Typetall (modus):** Verdien som forekommer oftest.

**Minimum og maksimum:** Laveste og høyeste verdi.

**Variasjonsbredde:** Maksimum minus minimum.

**Prosentandel:** Delmengde delt på totalen, multiplisert med 100.

Eksempel: Tallene 2, 3, 3, 4, 18.
- Sum = 30.
- Gjennomsnitt = 30/5 = 6.
- Median = 3.
- Typetall = 3.
- Variasjonsbredde = 18 - 2 = 16.

Gjennomsnittet er 6, mens medianen er 3. Verdien 18 trekker gjennomsnittet opp. Hvis du beskriver en typisk observasjon i et skjevt datasett, kan medianen være mer representativ.

## 13.6 Korrelasjon og årsakssammenheng

Korrelasjon betyr at to variabler varierer sammen. Det beviser ikke at den ene forårsaker den andre.

Eksempel: Iskremsalg og antall drukningsulykker kan begge øke om sommeren. Det betyr ikke at iskremsalg fører til drukning. En tredje variabel – varmt vær og flere mennesker som bader – kan påvirke begge.

Når du tolker et datasett, spør:
- Kan det finnes en tredje forklaringsvariabel?
- Er utvalget representativt?
- Er dataene samlet inn på samme måte?
- Er det sesongvariasjoner?
- Kan det være målefeil?
- Er sammenhengen sterk eller bare tilfeldig?

## 13.7 Visualisering

Velg diagram etter spørsmålet:

- **Søylediagram:** Sammenligne kategorier.
- **Linjediagram:** Vise utvikling over tid.
- **Punktdiagram:** Undersøke forhold mellom to numeriske variabler.
- **Histogram:** Vise fordeling av numeriske verdier.
- **Kakediagram:** Vise andeler av en helhet, men bare når få kategorier og tydelige andeler gjør det lesbart.

En god visualisering har tydelig tittel, forklarte akser, enheter, lesbar skala og kilde. Unngå å manipulere inntrykket med avkuttede akser eller utydelige kategorier.

## 13.8 Python-eksempel – lese CSV og beregne gjennomsnitt

```python
import csv

målinger = []

with open("temperatur.csv", encoding="utf-8", newline="") as fil:
    leser = csv.DictReader(fil)
    for rad in leser:
        try:
            temperatur = float(rad["temperatur_c"])
            målinger.append(temperatur)
        except (ValueError, KeyError):
            # Registrer eller hopp over ugyldige rader.
            continue

if målinger:
    gjennomsnitt = sum(målinger) / len(målinger)
    print("Antall målinger:", len(målinger))
    print("Gjennomsnitt:", round(gjennomsnitt, 2))
else:
    print("Ingen gyldige målinger")
```

Forklaring:
- `csv.DictReader` leser hver rad som en dictionary med kolonnenavn som nøkler.
- `float` gjør tekst om til desimaltall.
- `try/except` håndterer ugyldige verdier eller manglende kolonner.
- `målinger` samler gyldige temperaturer.
- `if målinger` hindrer deling på null hvis ingen gyldige målinger finnes.
- `round` avrunder resultatet.

Dette er et lite, men reelt dataanalyseforløp: innlesing, konvertering, feilhåndtering, beregning og presentasjon.

## 13.9 Metodiske begrensninger

Hvis du bruker data fra en spørreundersøkelse på nett, kan de som svarer være mer interessert i temaet enn de som ikke svarer. Det kan gi skjevhet. Hvis du bare undersøker én skole, kan du ikke uten videre generalisere til alle skoler i Norge.

Skille mellom:
- **Populasjon:** Hele gruppen du ønsker kunnskap om.
- **Utvalg:** De enhetene du faktisk undersøker.
- **Representativitet:** Hvor godt utvalget gjenspeiler populasjonen.
- **Reliabilitet:** Hvor pålitelig eller konsistent målingen er.
- **Validitet:** Om målingen faktisk undersøker det du ønsker å undersøke.

# KAPITTEL 14 – NETTVERK, WEB, HTTP OG API-ER

Dette er støttestoff til målene om informasjonssystemer, datautveksling, design og teknologi i samfunnet. Det er ikke et eget kompetansemål med krav om at alle skal kunne drifte et nettverk, men grunnforståelsen gjør det lettere å forklare hvordan moderne informasjonssystemer henger sammen.

## 14.1 Nettverk

Et datanettverk kobler sammen enheter slik at de kan utveksle data. Et lokalt nettverk (LAN) brukes ofte i hjem eller virksomheter. Internett er et globalt nettverk av nettverk.

- **Klient:** En enhet eller applikasjon som ber om en tjeneste.
- **Server:** En enhet eller programvare som tilbyr en tjeneste.
- **Ruter:** Sender trafikk mellom nettverk.
- **IP-adresse:** Identifiserer et nettverksgrensesnitt på IP-nettverk.
- **DNS:** Oversetter domenenavn til IP-adresser.
- **Protokoll:** Avtalt regelsett for kommunikasjon.

## 14.2 Klient–server

I en klient–server-modell sender klienten en forespørsel, og serveren behandler den og sender svar. Nettleseren kan være klient. En webserver leverer nettsiden eller data.

Fordeler:
- data kan samles og administreres sentralt,
- flere klienter kan bruke samme tjeneste,
- oppdateringer kan gjøres på serversiden.

Ulemper:
- serverfeil kan gjøre tjenesten utilgjengelig,
- nettverk kan være en flaskehals,
- serveren må beskyttes mot angrep,
- driftskostnader og kapasitet må håndteres.

## 14.3 HTTP og HTTPS

HTTP er en protokoll for å overføre forespørsler og svar mellom klient og server. En HTTP-forespørsel inneholder typisk metode, adresse, headere og eventuelt en body.

Vanlige metoder:
- `GET`: Hente data.
- `POST`: Sende data eller opprette en ressurs.
- `PUT`: Erstatte eller oppdatere en ressurs.
- `PATCH`: Delvis oppdatere en ressurs.
- `DELETE`: Slette en ressurs.

HTTPS er HTTP beskyttet med TLS. TLS bidrar til kryptering, autentisering av server og integritet i kommunikasjonen. HTTPS gjør ikke automatisk en app sikker; serverlogikk, tilgangskontroll og lagring må også være forsvarlig.

## 14.4 Statuskoder

- 200: OK – forespørselen lyktes.
- 201: Created – ressurs opprettet.
- 400: Bad Request – ugyldig forespørsel.
- 401: Unauthorized – autentisering mangler eller er ugyldig.
- 403: Forbidden – tilgang nektes.
- 404: Not Found – ressursen finnes ikke.
- 500: Internal Server Error – serverfeil.

Det er nyttig å kunne forklare at statuskoden forteller noe om resultatet, men at mer informasjon ofte finnes i svarkroppen eller loggene.

## 14.5 API

Et API (Application Programming Interface) er et grensesnitt som gjør at ett program kan bruke funksjoner eller data fra et annet system. Et web-API kan for eksempel tilby adresser som lar en app hente værdata eller registrere en bestilling.

Et REST-lignende API bruker ofte HTTP-metoder og ressurser. Data sendes ofte som JSON.

Eksempel på JSON-svar:

```json
{
  "city": "Oslo",
  "temperature": 4.2,
  "unit": "C"
}
```

Et API må dokumentere endepunkter, parametere, datatyper, autentisering, feil og begrensninger. API-nøkler og passord må ikke hardkodes offentlig i klientkode eller legges i et åpent repository.

## 14.6 Synkron og asynkron kommunikasjon

Ved synkron kommunikasjon venter programmet typisk på svar før det fortsetter. Ved asynkron kommunikasjon kan programmet fortsette mens en operasjon pågår, og håndtere svaret når det kommer.

Asynkron kommunikasjon er nyttig når nettverkskall tar tid. Brukergrensesnittet kan fortsatt reagere mens data lastes inn.

# KAPITTEL 15 – INFORMASJONSSIKKERHET

## 15.1 Hva er informasjonssikkerhet?

Informasjonssikkerhet handler om å beskytte informasjon og systemer mot uautorisert tilgang, endring, tap, ødeleggelse og utilgjengelighet. Målet er å sørge for at informasjon er tilgjengelig for riktige personer, riktig og når den trengs.

## 15.2 CIA-triaden

Tre sentrale mål:

- **Konfidensialitet:** Bare autoriserte personer skal få tilgang.
- **Integritet:** Informasjon skal være korrekt og ikke endres uautorisert.
- **Tilgjengelighet:** System og data skal være tilgjengelig når det trengs.

Eksempel fra helsevesenet:
- Konfidensialitet: uvedkommende skal ikke lese pasientjournalen.
- Integritet: journalen skal ikke endres uten autorisasjon og sporbarhet.
- Tilgjengelighet: helsepersonell må få tilgang når det er nødvendig.

Sikkerhetstiltak må balansere alle tre. En ekstremt låst løsning kan beskytte konfidensialitet, men gjøre data utilgjengelige når helsepersonell trenger dem.

## 15.3 Trusler, sårbarheter og risiko

- **Trussel:** Noe som kan forårsake skade, for eksempel en angriper, brann, feil eller skadevare.
- **Sårbarhet:** En svakhet som kan utnyttes, for eksempel svakt passord eller utdatert programvare.
- **Konsekvens:** Hva som skjer hvis hendelsen inntreffer.
- **Sannsynlighet:** Hvor sannsynlig det er at hendelsen skjer.
- **Risiko:** En vurdering av sannsynlighet og konsekvens.

En enkel risikovurdering rangerer både sannsynlighet og konsekvens, for eksempel lav, middels eller høy. Høy risiko krever ofte sterkere tiltak.

## 15.4 Autentisering og autorisasjon

**Autentisering** bekrefter hvem du er. Eksempler er passord, sikkerhetsnøkkel, biometrisk innlogging eller engangskode.

**Autorisasjon** bestemmer hva du får lov til å gjøre etter at identiteten er bekreftet. En vanlig bruker kan kanskje se sine egne data, mens en administrator kan administrere brukere.

Tofaktorautentisering (2FA/MFA) bruker mer enn én faktor, for eksempel noe du vet (passord), noe du har (mobil/sikkerhetsnøkkel) eller noe du er (biometri).

Prinsippet om minste privilegium betyr at en bruker eller tjeneste bare skal ha de rettighetene som er nødvendige for oppgaven.

## 15.5 Kryptering og hashing

**Kryptering** gjør data uleselige uten riktig nøkkel. Den brukes for å beskytte data under lagring og overføring.

- Symmetrisk kryptering bruker samme hemmelige nøkkel til kryptering og dekryptering.
- Asymmetrisk kryptering bruker et nøkkelpar: offentlig og privat nøkkel.

**Hashing** gjør data om til en hashverdi. Hashing er normalt enveis og brukes blant annet til integritetskontroll og passordlagring. Passord skal ikke lagres i klartekst. Bruk spesialiserte, trege passordhashfunksjoner med salt, som Argon2, bcrypt eller scrypt.

Kryptering og hashing er ikke det samme. Kryptert data kan dekrypteres med nøkkel; en hash er ikke ment å reverseres.

## 15.6 Sikkerhetskopi og gjenoppretting

Backup er en kopi av data som kan brukes hvis originalen går tapt eller blir ødelagt. En backup er først nyttig hvis den kan gjenopprettes.

En robust rutine bør beskrive:
- hva som sikkerhetskopieres,
- hvor ofte,
- hvor kopien lagres,
- hvem som har tilgang,
- hvor lenge kopier beholdes,
- hvordan gjenoppretting testes.

3-2-1-prinsippet er en vanlig tommelfingerregel: tre kopier av data, på to ulike typer lagringsmedier, med én kopi utenfor hovedlokasjonen. Det er et prinsipp, ikke en absolutt lov.

## 15.7 Vanlige angrep og beskyttelse

**Phishing:** Angriper forsøker å lure brukeren til å oppgi passord eller åpne skadelig innhold. Beskyttelse: opplæring, MFA, kontroll av avsender og lenker.

**Skadevare:** Programvare som gjør skade, for eksempel virus, trojaner eller ransomware. Beskyttelse: oppdateringer, begrensede rettigheter, sikkerhetskopier og beskyttelsesverktøy.

**Brute force:** Mange passordforsøk. Beskyttelse: MFA, rate limiting, sterke passord og overvåking.

**SQL-injeksjon:** Utrygg håndtering av brukerinput gjør at angriper kan påvirke SQL-spørringer. Beskyttelse: parameteriserte spørringer, validering og minst privilegium.

**Cross-site scripting (XSS):** Utrygg innsetting av brukerinnhold kan gjøre at skript kjøres i andre brukeres nettleser. Beskyttelse: korrekt output-escaping, sikker håndtering av input og moderne sikkerhetsmekanismer.

**Tjenestenekt (DoS/DDoS):** Systemet overbelastes slik at legitime brukere ikke kommer til. Beskyttelse kan være trafikkfiltrering, begrensning, kapasitet og beredskap.

OWASP Top 10 er en kjent oversikt over sentrale risikoer for webapplikasjoner. Bruk den som en referanse for bevissthet, ikke som hele pensum.

# KAPITTEL 16 – MUNTLIG FAGLIG FORMIDLING

## 16.1 Vis kompetanse – ikke bare husk definisjoner

På muntlig-praktisk eksamen må du få kunnskapen ut av hodet og inn i en forklaring eller handling. Et kort, presist svar er ofte bedre enn en lang forklaring som mister retningen. Samtidig må du kunne utdype når sensor spør «hvorfor?» eller «kan du vise det?».

Bruk denne strukturen når du forklarer en teknisk løsning:

1. **Hva:** Hva er løsningen eller begrepet?
2. **Hvordan:** Hvordan fungerer det konkret?
3. **Hvorfor:** Hvorfor valgte du denne tilnærmingen?
4. **Eksempel:** Vis det med kode, modell eller en konkret situasjon.
5. **Vurdering:** Hvilke styrker, svakheter eller alternativer finnes?

Eksempel på OOP-svar:

«Jeg har laget klassene `Bok`, `Medlem` og `Lån`. `Bok` lagrer informasjon om boka, mens `Lån` knytter en bok til et medlem og lagrer dato og frist. Jeg valgte `Lån` som egen klasse fordi relasjonen har egne opplysninger. Det gjør modellen tydeligere enn å bare lagre en liste med medlemsnumre i `Bok`. Jeg ville også testet at samme bok ikke kan lånes ut til to personer samtidig.»

Dette viser mer kompetanse enn å si «OOP er objektorientert programmering».

## 16.2 Når du ikke vet svaret umiddelbart

Ikke gjett vilt. Vis hvordan du resonnerer:

- «Jeg er ikke helt sikker på den eksakte betegnelsen, men jeg tror problemet handler om …»
- «Jeg ville først undersøkt … fordi …»
- «En mulig løsning er … En annen løsning kan være …»
- «For å kontrollere dette ville jeg testet …»

Det er bedre å vise relevant tankegang enn å bli stille. Hvis du er usikker på et begrep, prøv å forklare funksjonen med egne ord.

## 16.3 Vanlige oppfølgingsspørsmål

Sensor kan spørre:
- Hvorfor valgte du denne løsningen?
- Hvilke alternativer vurderte du?
- Hva skjer hvis input er tom eller ugyldig?
- Hvordan vet du at programmet virker?
- Hvilken del ville du forbedret først?
- Hva skjer hvis datamengden blir mye større?
- Hvem har tilgang til dataene?
- Hvordan ville du gjort løsningen mer brukervennlig?
- Hva er ulempen ved å bruke arv her?
- Hvordan kan dette gjenbrukes i et annet program?

## 16.4 Forklar kode mens du demonstrerer

Når du viser kode, ikke les hver linje ordrett. Forklar først målet, deretter de viktigste delene.

Eksempel:

«Denne funksjonen tar imot en liste med temperaturer. Først sjekker jeg om listen er tom, slik at jeg ikke deler på null. Deretter summerer jeg verdiene og deler på antallet. Jeg returnerer gjennomsnittet, slik at andre deler av programmet kan bruke resultatet. Jeg ville testet med en vanlig liste, en liste med ett element og en tom liste.»

## 16.5 Når sensor ber deg drøfte

En drøfting er ikke bare å ramse opp fordeler og ulemper. Du må forklare hvorfor argumentene har betydning og vise hvilke hensyn som veier tyngst.

En god struktur:
- Avklar formålet.
- Identifiser interessenter.
- Forklar fordeler.
- Forklar ulemper og risiko.
- Foreslå tiltak eller alternativer.
- Gi en begrunnet konklusjon.

## 16.6 Muntlig øvelse – teach-back

Etter hvert kapittel: lukk teksten og forklar innholdet høyt i 60–120 sekunder som om du underviser en annen elev. Ta opptak hvis det hjelper, men ikke bruk tid på redigering. Lytt etter:
- brukte du fagbegreper riktig?
- ga du et konkret eksempel?
- forklarte du hvorfor?
- sa du noe om begrensninger eller alternativer?
- kunne du svart på et oppfølgingsspørsmål?

## CASE 5 – Booking av gruppetimer

### Oppgave

Et treningssenter trenger et program der brukere kan se gruppetimer, bestille plass og avbestille. Timene har maks kapasitet. Brukeren skal få tydelig beskjed hvis en time er full.

Du skal:
1. foreslå en struktur for data og klasser,
2. beskrive de viktigste funksjonene,
3. demonstrere bestilling med kontroll av kapasitet,
4. lage relevante testtilfeller,
5. vurdere brukervennlighet og tilgjengelighet.

### Eksempel på logikk

```python
class Gruppetime:
    def __init__(self, navn, kapasitet):
        self.navn = navn
        self.kapasitet = kapasitet
        self.bookinger = []

    def book(self, medlem_id):
        if medlem_id in self.bookinger:
            return "Du har allerede plass"
        if len(self.bookinger) >= self.kapasitet:
            return "Timen er full"
        self.bookinger.append(medlem_id)
        return "Bestilling bekreftet"
```

- Prøv ugyldig medlem-ID.

## 25. Fordypning: Fra brukerbehov til robust programdesign

### 25.1 Problemet må forstås før løsningen velges

En vanlig feil i programutvikling er å begynne med den teknologien utvikleren kjenner best. Riktig arbeidsrekkefølge er å forstå behovet først. Et brukerbehov beskriver hva en person må få gjort, mens en teknisk løsning beskriver hvordan systemet skal støtte dette.

Tenk deg at en skole ber om «en app for fravær». Det er for lite informasjon til å begynne å programmere. Du må spørre: Hvem registrerer fravær? Skal elever kunne melde fravær selv? Skal foresatte få varsler? Hvem kan se helseopplysninger? Må systemet kobles til et eksisterende elevregister? Hvor lenge skal data lagres? Hva skjer hvis nettverket er nede?

Et godt design oppstår når kravene blir tydelige nok til at det går an å vurdere løsningene. Det er vanlig å skille mellom interessenter, funksjonelle krav, kvalitetskrav og rammebetingelser.

### 25.2 Brukerhistorier og akseptansekriterier

En brukerhistorie beskriver et behov fra brukerens perspektiv:

«Som bibliotekansatt vil jeg kunne se hvilke bøker som er utlånt, slik at jeg kan svare på spørsmål fra besøkende.»

Akseptansekriterier beskriver hvordan vi vet at behovet er oppfylt:
- Ansatt kan søke på tittel, forfatter eller ISBN.
- Resultatet viser om boka er tilgjengelig.
- Hvis boka er utlånt, vises forventet innleveringsdato når dette er tillatt.
- Søket skal gi en forståelig beskjed hvis ingen treff finnes.

Akseptansekriterier kan gjøres om til tester. Det er en viktig sammenheng: krav → design → implementering → test.

### 25.3 Avveininger i design

Det finnes sjelden en løsning som er best på alle områder. En enkel filbasert løsning kan være lett å lage og billig å drifte, men svakere ved samtidige brukere og relasjoner. En database kan gi bedre søk, transaksjoner og integritet, men krever mer oppsett og administrasjon.

Et godt svar på eksamen bør derfor ikke si «database er alltid best». Si heller: «For en liten liste med én bruker kan JSON være tilstrekkelig. Når flere ansatte skal oppdatere utlån samtidig, og vi trenger relasjoner mellom medlemmer, bøker og lån, ville jeg valgt en relasjonsdatabase. Det gir bedre håndtering av relasjoner og samtidige endringer, men krever mer administrasjon.»

### 25.4 Robusthet og feiltilstander

En robust løsning forventer at ting kan gå galt. Brukeren kan skrive feil input. En fil kan mangle. Nettverket kan være nede. En database kan avvise en oppdatering. En API-tjeneste kan svare sakte.

Design derfor for:
- ugyldige data,
- tomme felt,
- manglende ressurser,
- utilgjengelige tjenester,
- dobbeltklikk eller gjentatte forespørsler,
- samtidige brukere,
- avbrutt operasjon.

Robusthet betyr ikke at programmet aldri feiler. Det betyr at feil håndteres på en kontrollert måte, at data ikke blir ødelagt, og at brukeren får en forståelig beskjed.

### 25.5 Eksempel: Bestilling med lagerbeholdning

En nettbutikk har ett produkt igjen. To kunder trykker «Kjøp» omtrent samtidig. Hvis begge klientene først leser lagerbeholdning = 1 og deretter sender bestilling, kan systemet ende med å selge to produkter.

Dette er et samtidighetsproblem. Kontroll bare i brukergrensesnittet er ikke nok. Serveren/databasen må håndtere lagerreduksjon på en sikker måte, gjerne i en transaksjon eller med en betinget oppdatering som bare lykkes dersom lageret fortsatt er større enn null.

Dette eksempelet viser hvorfor programdesign, database, testing og sikkerhet henger sammen.

### Fordypningsoppgaver

1. Lag fem brukerhistorier for et digitalt bibliotek. Skriv minst to akseptansekriterier for hver.
2. Et system skal brukes av 50 ansatte samtidig. Vurder hvordan det påvirker valg av lagring, autentisering og feilhåndtering.
3. Et bestillingssystem registrerer samme ordre to ganger når brukeren dobbeltklikker. Forklar hvordan du vil undersøke og løse problemet.
4. Sammenlign en enkel løsning som er rask å utvikle med en mer robust løsning som tar lengre tid. Når kan det være riktig å velge den enkle?

## 26. Fordypning: Testing som en planlagt del av utviklingen

### 26.1 Testing er mer enn å trykke på knappen

Når en utvikler manuelt prøver en funksjon én gang og ser at den fungerer, har utvikleren bare vist at én bestemt situasjon fungerte. Det sier lite om andre inputverdier, feiltilstander, brukerroller og kombinasjoner av handlinger.

En test bør ha et tydelig formål. Du bør vite hva som kontrolleres, hvilke forutsetninger som gjelder, hvilke data som brukes, hvilket resultat som forventes, og hva som faktisk skjedde.

### 26.2 Testdekning

Testdekning beskriver hvor stor del av programmet eller kravene som er testet. Høy testdekning betyr ikke automatisk høy kvalitet. En test kan kjøre gjennom en linje uten å kontrollere om resultatet er riktig.

Det er nyttig å skille mellom:
- linjedekning: hvilke kodelinjer som er kjørt,
- grendekning: om ulike valg/greiner i betingelser er testet,
- kravedekning: om kravene har tilhørende tester,
- tilstandsovergangsdekning: om viktige tilstandsendringer er testet.

### 26.3 Test først – TDD som metode

Testdrevet utvikling (TDD) er en metode der utvikleren skriver en test før selve funksjonen implementeres. En vanlig syklus er:

1. Skriv en test som feiler fordi funksjonen ikke finnes eller ikke fungerer.
2. Skriv den enkleste koden som gjør at testen består.
3. Rydd opp i koden uten å endre oppførselen.
4. Kjør testene på nytt.

Du trenger ikke bruke TDD i alle prosjekter, men metoden viser hvordan tester kan styre utviklingen og avklare forventet oppførsel.

### 26.4 Mock og testdata

En mock er en kontrollert erstatning for en komponent som normalt kommuniserer med noe eksternt. Hvis funksjonen henter værdata fra internett, kan en mock gi et fast svar slik at testen ikke er avhengig av et ekte API.

Testdata bør være:
- normale,
- på grensen,
- ugyldige,
- tomme,
- store nok til å avdekke ytelsesproblemer der det er relevant,
- utformet slik at personopplysninger ikke brukes unødvendig.

### 26.5 Feilrapport

En god feilrapport inneholder:
- kort beskrivelse,
- steg for å gjenskape feilen,
- forventet resultat,
- faktisk resultat,
- skjermbilde/logg ved behov,
- programversjon og miljø,
- alvorlighetsgrad og hvor ofte feilen oppstår.

### Eksempel: Utlånssystem

Feil: Boka kan lånes ut to ganger.

Gjenskaping:
1. Opprett én bok.
2. Opprett to medlemmer.
3. Lån boka til medlem A.
4. Prøv å låne samme bok til medlem B.

Forventet: Andre utlån avvises.
Faktisk: Systemet oppretter et nytt lån.
Mulig rotårsak: Metoden kontrollerer ikke tilgjengelighet før den oppretter lånet, eller kontrollerer ikke på en atomisk måte ved samtidige brukere.

Rettelse: Legg valideringen i domenelogikken/serveren og sørg for at datalagringen ikke tillater motstridende aktive lån. Test både vanlig og samtidig bruk dersom systemet støtter flere brukere.

### Fordypningsoppgaver

1. Lag en testplan med minst seks testtilfeller for en passordvalidator.
2. Forklar hvorfor enhetstester ikke erstatter akseptansetester.
3. Skriv en god feilrapport for en funksjon som viser feil dato etter midnatt.
4. Forklar hvordan en mock kan brukes når du tester en funksjon som henter data fra et API.

## 27. Fordypning: Kodekvalitet, avhengigheter og refaktorering

### 27.1 Sammenheng og avhengighet

To viktige designbegreper er kohesjon og kobling.

- **Kohesjon (sammenheng):** Hvor godt delene i en modul hører sammen. En klasse med ett tydelig ansvar har ofte høy kohesjon.
- **Kobling (avhengighet):** Hvor sterkt én modul er avhengig av detaljer i en annen. Lav kobling gjør systemet enklere å endre.

En klasse `Bestilling` bør ikke samtidig håndtere visning av knapper, e-postsending, SQL-tilkobling, utskrift og rabatteregler. Det er flere ulike ansvarsområder. Ved å dele opp systemet kan hver del testes og endres mer selvstendig.

### 27.2 Refaktorering

Refaktorering er å forbedre intern kodekvalitet uten å endre hva programmet gjør for brukeren. Eksempler:
- gi variabler og funksjoner bedre navn,
- dele en lang funksjon i mindre funksjoner,
- fjerne duplisert kode,
- flytte ansvar til riktig klasse,
- redusere unødvendige avhengigheter,
- legge til tester før større endringer.

Refaktorering bør skje gradvis og med tester. Hvis du endrer både logikk og struktur samtidig, blir det vanskelig å finne årsaken hvis resultatet endres.

### 27.3 Kodegjennomgang

Kodegjennomgang (code review) betyr at en annen utvikler leser endringer før de tas inn i hovedversjonen. Målet er å oppdage feil, forbedre lesbarhet, dele kunnskap og sikre at teamet følger felles regler.

En god gjennomgang vurderer:
- om løsningen dekker kravene,
- om koden er forståelig,
- om feiltilstander er håndtert,
- om data beskyttes,
- om testene dekker relevante situasjoner,
- om endringen er større enn nødvendig.

### Fordypningsoppgaver

1. En funksjon på 150 linjer gjør fem ulike ting. Forklar hvordan du vil refaktorere den.
2. Forklar forskjellen mellom høy kohesjon og lav kobling.
3. Hvorfor er det lurt å bruke tester når kode refaktoreres?
4. Beskriv hva en code review kan oppdage som automatiske tester ikke finner.

## 28. Fordypning: Brukertesting, heuristikker og universell utforming

### 28.1 Brukertesting i praksis

En brukertest starter med et spørsmål du ønsker svar på. Du lager en realistisk oppgave, velger representative brukere, observerer hvordan de arbeider og samler funn.

Ikke spør bare «liker du appen?». Det gir ofte høflige og lite konkrete svar. Be brukeren utføre oppgaven:
- «Finn produktet og legg det i handlekurven.»
- «Bestill en gruppetime neste tirsdag.»
- «Endre telefonnummeret ditt.»

Observer om brukeren finner riktig sted, misforstår etiketter, trykker feil, trenger hjelp eller avbryter. Etterpå kan du spørre hva som var vanskelig og hvorfor.

### 28.2 Heuristikker

Heuristikker er generelle prinsipper for brukervennlig design. Noen sentrale prinsipper:
- Vis systemstatus: brukeren må forstå hva som skjer.
- Bruk et språk som passer målgruppen.
- Gi brukeren kontroll og mulighet til å angre.
- Vær konsekvent.
- Forebygg feil fremfor å bare vise feilmeldinger.
- Ikke krev at brukeren husker unødvendig informasjon.
- Gi hjelpetekst når den trengs.

### 28.3 Tilgjengelighet er mer enn skjermleser

Tilgjengelighet handler om at personer med ulike behov kan bruke systemet. Dette kan omfatte syn, hørsel, motorikk, kognitive utfordringer, språk og situasjon.

Eksempler:
- Tekstkontrast må være tilstrekkelig.
- Funksjoner må kunne nås med tastatur.
- Fokusmarkering må være synlig.
- Skjemafelt må ha etiketter.
- Feil må forklares i tekst, ikke bare med rødt felt.
- Lyd og video må ha tekstalternativer der det er relevant.
- Klikkbare områder bør være store nok.
- Bevegelser og blinkende innhold må ikke skape unødig belastning.

### 28.4 A/B-testing og måling

A/B-testing sammenligner to varianter av et grensesnitt for å se hvilken som gir bedre resultat på en definert måling. Det kan være fullføringsgrad, tid eller feilrate. Men målingen må passe formålet. Hvis du bare måler hvor fort brukeren gjennomfører et skjema, kan du overse om brukeren forstår hva som skjer eller gir riktige opplysninger.

### Fordypningsoppgaver

1. Lag tre brukertestoppgaver for en kommunal søknadsportal.
2. Beskriv hvordan du vil gjøre en app mer tilgjengelig for tastaturbrukere.
3. Hvilke måleparametere ville du bruke for å vurdere om et nytt bestillingsskjema er bedre enn det gamle?
4. Forklar hvorfor «flest mulig funksjoner» ikke nødvendigvis gir god brukervennlighet.

## 29. Fordypning: Data, schema, kvalitet og sporbarhet

### 29.1 Skjema og datakontrakt

Et skjema beskriver hvordan data skal se ut. Det kan angi feltnavn, datatyper, obligatoriske felt, tillatte verdier og relasjoner.

Eksempel på en datakontrakt for en bestilling:
- `order_id`: unik tekst eller heltall.
- `customer_id`: referanse til en kunde.
- `created_at`: tidspunkt med avtalt format og tidssone.
- `items`: liste med ordrelinjer.
- `total`: beløp i avtalt valuta.

Hvis ett system sender `created_at` i lokal tid og et annet tolker verdien som UTC, kan tidspunktet bli feil. Standarder for format og tidssone er derfor viktige.

### 29.2 Datatyper og validering

En datakolonne som ser ut som tall, er ikke nødvendigvis lagret som tall. Hvis verdien «19» lagres som tekst, kan sortering bli alfabetisk i stedet for numerisk. Det samme gjelder datoer.

Validering kontrollerer om dataene følger reglene. Det kan være:
- typekontroll,
- formatkontroll,
- områdekontroll,
- kontroll av obligatoriske felt,
- kontroll av relasjoner,
- kontroll av unike verdier.

Validering på brukerens enhet gir god tilbakemelding, men serveren må også kontrollere dataene. Klientkode kan manipuleres.

### 29.3 Sporbarhet og metadata

Metadata er data om data. Et datasett bør ha informasjon om kilde, tidspunkt, måleenhet, metode, eier, versjon og eventuelle begrensninger. Uten slik kontekst kan en analyse bli misvisende.

Sporbarhet handler om å kunne forstå hvor data kom fra, hvilke endringer som ble gjort, og hvordan et resultat ble produsert. Det er viktig for feilsøking, personvern og etterprøvbarhet.

### Fordypningsoppgaver

1. Lag et enkelt skjema for en elevregistrering. Hvilke felt er nødvendige, og hvilke er personvernmessig unødvendige?
2. Forklar hvorfor dato og tidssone må standardiseres i systemer som brukes på tvers av land.
3. Hva er metadata, og hvordan kan metadata gjøre et datasett mer nyttig?
4. Forklar hvorfor samme validering bør gjøres på serveren selv om nettleseren allerede kontrollerer input.

## 30. Fordypning: Nettverk, API-er og feil i distribuerte systemer

### 30.1 Nettverk er ikke alltid pålitelige

Et program som bruker nettverk, må forvente at forespørsler kan feile. Serveren kan være nede, nettverket kan være ustabilt, forespørselen kan ta for lang tid, eller svaret kan være ugyldig.

En robust klient bør ha:
- timeout,
- forståelig feilmelding,
- kontroll av statuskode,
- validering av svardata,
- begrenset retry når det passer,
- sikker håndtering av hemmeligheter.

Retry betyr å prøve på nytt. Det er ikke alltid trygt. Hvis et betalingskall gjennomføres på nytt uten kontroll, kan kunden bli belastet flere ganger. Idempotens er et viktig begrep: en operasjon er idempotent hvis gjentakelse med samme input ikke gir flere uønskede effekter.

### 30.2 API-versjonering og dokumentasjon

Når et API endres, kan gamle klienter slutte å virke. Versjonering gjør det mulig å kommunisere hvilke regler og felter en klient bruker. Dokumentasjon bør vise eksempel på forespørsel, svar, feil og autentisering.

### 30.3 Caching

Caching lagrer en midlertidig kopi av data for raskere tilgang og mindre belastning. Men hurtigbuffer kan inneholde utdaterte data. Systemet må vite når informasjon skal oppdateres eller fjernes.

### Fordypningsoppgaver

## 31. Fordypning: Trusselmodellering og sikker utvikling

### 31.1 Sikkerhet må bygges inn tidlig

Sikkerhet bør planlegges fra starten, ikke legges på helt til slutt. Når du tegner dataflyt og arkitektur, bør du spørre:
- Hvilke data er verdifulle eller sensitive?
- Hvem skal bruke systemet?
- Hvilke komponenter er tilgjengelige fra internett?
- Hvor er tillitsgrensene?
- Hvordan kan en angriper misbruke funksjoner?
- Hvilke tiltak reduserer sannsynlighet og konsekvens?

Dette er enkel trusselmodellering.

### 31.2 Tillitsgrenser

En tillitsgrense skiller områder der vi ikke kan anta samme grad av tillit. Nettleseren er ikke en sikker kontrollflate for serveren, fordi brukeren kan endre forespørsler. En fil lastet opp av en ukjent bruker bør behandles som utrygg. Data fra et eksternt API må valideres.

### 31.3 Sikker utviklingspraksis

- Valider alle input.
- Bruk parameteriserte SQL-spørringer.
- Beskytt API-nøkler og passord.
- Gi brukere minst nødvendige rettigheter.
- Oppdater biblioteker og rammeverk.
- Ikke lagre passord i klartekst.
- Krypter sensitive data under overføring.
- Logg relevante sikkerhetshendelser, men ikke lekk sensitive data i loggene.
- Test tilgangskontroll med ulike brukerroller.
- Ha en plan for sikkerhetskopi og gjenoppretting.

### 31.4 Sikkerhetseksempel: Skoleportal

En skoleportal har elever, foresatte, lærere og administratorer. En elev skal ikke kunne lese andre elevers fraværsdata ved å endre en ID i URL-en. Dette er et tilgangskontrollproblem. Serveren må kontrollere at den innloggede brukeren har rett til akkurat den ressursen, ikke bare at brukeren er logget inn.

### Fordypningsoppgaver

3. Beskriv hvordan en elev kan få tilgang til data de ikke skal se dersom autorisasjon mangler.
4. Hvilke data bør ikke havne i en feillogg?

## 32. Ekstra praktiske kodeoppgaver – med veiledning

### Oppgave 1 – Tell verdier over en grense

Skriv en funksjon som tar imot en liste med tall og returnerer hvor mange tall som er større enn 10.

Mulig løsning:

```python
def tell_over_ti(talliste):
    antall = 0
    for tall in talliste:
        if tall > 10:
            antall += 1
    return antall
```

Forklaring: Vi starter på null, går gjennom hvert element, tester betingelsen og øker telleren når den er sann. Test med tom liste, bare tall under 10, tall lik 10 og tall over 10.

### Oppgave 2 – Finn gjennomsnitt

```python
def gjennomsnitt(talliste):
    if len(talliste) == 0:
        return None
    return sum(talliste) / len(talliste)
```

Forklaring: Den tomme listen må håndteres fordi vi ellers deler på null. Alternativt kan funksjonen kaste en exception hvis tom liste ikke er tillatt.

### Oppgave 3 – Enkel klasse for produkt

```python
class Produkt:
    def __init__(self, navn, pris, lager):
        self.navn = navn
        self.pris = pris
        self.lager = lager

    def er_tilgjengelig(self):
        return self.lager > 0

    def ta_fra_lager(self, antall):
        if antall <= 0:
            return False
        if antall > self.lager:
            return False
        self.lager -= antall
        return True
```

Sensor kan spørre: Hva skjer hvis prisen er negativ? Hvordan kan du hindre ugyldig produkt? Burde lagerendring styres av en egen lagerklasse? Hvordan tester du metoden?

### Oppgave 4 – Enkel arv

```python
class Ansatt:
    def __init__(self, navn, timelonn):
        self.navn = navn
        self.timelonn = timelonn

    def beregn_lonn(self, timer):
        return self.timelonn * timer

class Overtidsansatt(Ansatt):
    def beregn_lonn(self, timer):
        ordinare = min(timer, 37.5) * self.timelonn
        overtid = max(0, timer - 37.5) * self.timelonn * 1.5
        return ordinare + overtid
```

Forklar at `Overtidsansatt` er en type `Ansatt` og overstyrer beregningen. Sensor kan spørre om regelverket er hardkodet, hvordan satsen burde kunne endres, og hvordan dette testes.
