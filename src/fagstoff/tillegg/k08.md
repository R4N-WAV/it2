## Læringsmål

Etter dette kapittelet skal du kunne:

- forklare hva **gjenbrukbar kode** er, og hvorfor kopiering av kode gir feil når regler endres,
- bruke **parametere** og **returverdier** for å gjøre en funksjon generell,
- forklare **abstraksjon** («hva den gjør, ikke hvordan») og **grensesnitt**,
- forklare **DRY** og **KISS** – og når litt gjentakelse er greit,
- dele et program i **moduler** med tydelig ansvar, og forklare **høy kohesjon** og **lav kobling**,
- **refaktorere** en kodebit i små steg med tester,
- skrive gode navn og en **docstring**.

> TIPS: Kompetansemål 7 handler om å **generalisere**. Det viktigste spørsmålet å stille om en kodebit er: «Hva må endres hvis regelen endres – og hvor mange steder?»

## Flere eksempler

### Eksempel 1 (enkelt): Fra hardkodet til parameter

```python
# Før: tre nesten like funksjoner
def tell_over_ti(liste):
    return len([x for x in liste if x > 10])

def tell_over_hundre(liste):
    return len([x for x in liste if x > 100])

# Etter: én funksjon, grensen er en parameter
def tell_over(liste, grense):
    antall = 0
    for x in liste:
        if x > grense:
            antall += 1
    return antall

tell_over([5, 15, 150], 10)    # 2
tell_over([5, 15, 150], 100)   # 1
```

### Eksempel 2 (middels): Rabattregel kopiert fire steder

```python
# Kassen
pris = pris * 0.9 if medlem else pris
# Nettbutikken
total = total * 0.9 if er_medlem else total
# Kvittering
vist_pris = pris * 0.9 if kunde.medlem else pris
# Rapport
...
```

Når rabatten endres til 15 %, må fire steder endres – og ett blir glemt. Kunden ser én pris i nettbutikken og en annen på kvitteringen. Løsning:

```python
MEDLEMSRABATT = 0.10

def pris_etter_rabatt(pris, medlem):
    """Returnerer prisen etter medlemsrabatt.

    pris: beløp i kroner (>= 0)
    medlem: True hvis kunden er medlem
    """
    if pris < 0:
        raise ValueError("Pris kan ikke være negativ")
    return pris * (1 - MEDLEMSRABATT) if medlem else pris
```

Nå finnes regelen **ett** sted, den kan **testes** én gang, og navnet forklarer hensikten.

### Eksempel 3 (sammensatt): Moduler i en nettbutikk

```diagram
boks ui 1 0 grensesnitt.py: sider og knapper
boks kurv 0 1 handlekurv.py: legg_til, fjern, total
boks betaling 1 1 betaling.py: betal, kvittering
boks produkter 2 1 produkter.py: søk, hent

pil ui kurv
pil ui betaling
```

Hver modul har ett ansvar (**høy kohesjon**). Modulene snakker sammen via få, tydelige funksjoner (**lav kobling**). Hvis vi bytter database, endres bare `lagring.py`.

## Gjennomarbeidet eksempel

**Oppgave:** Refaktorer en lang funksjon som gjør alt.

```python
def behandle(filnavn):
    f = open(filnavn, encoding="utf-8")
    linjer = f.readlines()
    f.close()
    t = 0
    n = 0
    for l in linjer[1:]:
        d = l.strip().split(",")
        if d[2] != "":
            t = t + float(d[2])
            n = n + 1
    print("Snitt:", t / n)
```

Problemer: dårlige navn (`t`, `n`, `d`), lesing, beregning og utskrift i samme funksjon, krasjer ved null gyldige rader, kan ikke testes uten fil.

**Steg 1 – skriv en test av dagens oppførsel** (lag en liten testfil). **Steg 2 – del opp i én oppgave per funksjon:**

```python
import csv

def les_verdier(filnavn, kolonne):
    """Leser én numerisk kolonne fra en CSV-fil. Hopper over tomme/ugyldige felt."""
    verdier = []
    with open(filnavn, encoding="utf-8", newline="") as fil:
        for rad in csv.DictReader(fil):
            try:
                verdier.append(float(rad[kolonne]))
            except (ValueError, KeyError):
                continue
    return verdier

def gjennomsnitt(verdier):
    if not verdier:
        return None
    return sum(verdier) / len(verdier)

def vis_snitt(verdi):
    print("Ingen gyldige verdier" if verdi is None else f"Snitt: {verdi:.2f}")

vis_snitt(gjennomsnitt(les_verdier("temperatur.csv", "temperatur_c")))
```

**Steg 3 – kjør testen igjen.** **Gevinst:** `gjennomsnitt` kan testes uten fil, `les_verdier` kan gjenbrukes for andre kolonner, og feilhåndteringen ligger ett sted. Vi brukte også et **bibliotek** (`csv`) i stedet for å splitte på komma – også det er gjenbruk.

## Muntlig forklaring

Prøv selv: Forklar abstraksjon og hvorfor det gjør kode gjenbrukbar.

:::modell
«Abstraksjon betyr å skjule detaljene bak et enkelt grensesnitt. Når jeg bruker `sum(liste)`, trenger jeg bare å vite at den tar en liste og gir summen – ikke hvordan den er laget. På samme måte lager jeg funksjonen `pris_etter_rabatt(pris, medlem)`: resten av programmet trenger bare navnet, parameterne og returverdien. Det gjør koden gjenbrukbar, fordi kassen, nettbutikken og kvitteringen kan bruke samme funksjon, og når rabattregelen endres, endrer jeg ett sted. Det er DRY-prinsippet. Men jeg passer på KISS også: en 'alt-i-ett'-funksjon med 18 parametere er ikke god gjenbruk, den er bare vanskelig å bruke. God gjenbruk er små funksjoner med ett tydelig ansvar.»
:::

## Sensoroppfølging

1. «Er all gjentakelse dårlig?» – Nei; to blokker som ser like ut, men representerer ulike regler, bør kunne endres hver for seg.
2. «Hva er forskjellen på en funksjon og en modul?» – Funksjon = én oppgave; modul = fil/samling av relaterte funksjoner/klasser.
3. «Hvorfor er returverdi bedre enn print?» – Kan brukes videre og testes.
4. «Hva er refaktorering?» – Forbedre intern struktur uten å endre oppførsel, i små steg med tester.
5. «Hvordan kan klasser gi gjenbruk?» – Mange objekter fra samme mal, arv og polymorfisme.

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Hva er forskjellen mellom en funksjon og en modul?
:::losning
En funksjon er en navngitt kodeblokk som gjør én oppgave (`gjennomsnitt(liste)`). En modul er en større enhet – typisk en fil – som samler relaterte funksjoner, klasser og konstanter (`statistikk.py`), og som kan importeres i andre programmer (`import statistikk`).
:::

:::oppgave Grunnleggende
2. Hvorfor er det bedre å bruke en parameter enn å hardkode samme verdi i flere funksjoner?
:::losning
Med parameter kan samme funksjon brukes for mange verdier (grense 10, 100, 0), så vi slipper nesten like kopier. Endringer skjer ett sted, risikoen for at kopiene blir ulike forsvinner, og funksjonen er lett å teste med ulike verdier.
:::

:::oppgave Middels
3. En rabattberegning er kopiert fire steder i programmet. Forklar hvordan du vil gjøre den gjenbrukbar.
:::losning
Se eksempel 2: lag `pris_etter_rabatt(pris, medlem)` med rabattsatsen som konstant (eller parameter), legg den i en felles modul, skriv tester for grenser og ugyldig input, og erstatt de fire kopiene én om gangen mens testene kjøres.
:::

:::oppgave Middels
4. Del et lite bibliotekprogram inn i logiske moduler eller klasser.
:::losning
- `modeller.py`: klassene `Bok`, `Medlem`, `Lan`.
- `bibliotek.py`: `Bibliotek` med regler for utlån/innlevering og forfalte lån.
- `lagring.py`: lese/skrive til JSON eller database.
- `grensesnitt.py`: meny/skjerm og meldinger til brukeren.
- `test_bibliotek.py`: tester av reglene.
Reglene ligger i `bibliotek.py`, ikke i grensesnittet, så de kan testes og gjenbrukes.
:::

:::oppgave Utfordrende
5. Et team har laget en generisk «alt-i-ett»-funksjon med 18 parametere. Vurder om den er god gjenbrukbar kode, og foreslå forbedringer.
:::losning
Neppe. Den er vanskelig å forstå og bruke riktig (hvilke parametere hører sammen?), vanskelig å teste (enormt antall kombinasjoner), og en endring for ett bruksområde kan ødelegge et annet (høy kobling). Forbedringer: del i mindre funksjoner med ett ansvar; samle relaterte parametere i et objekt eller en ordbok (f.eks. `Innstillinger`); bruk standardverdier for sjeldne valg; vurder klasser med polymorfisme i stedet for mange `if`-flagg.
:::

:::oppgave Utfordrende
6. Forklar hvordan abstraksjon og tydelige grensesnitt reduserer avhengigheter i et større program.
:::losning
Når en modul bare tilbyr noen få, veldefinerte funksjoner (grensesnittet), trenger resten av programmet ikke kjenne de interne detaljene. Da kan innsiden endres – f.eks. bytte fra fil til database – uten at de som bruker modulen må endres. Avhengighetene går til grensesnittet, ikke til implementasjonen. Det gir lavere kobling, enklere testing (man kan erstatte en modul med en mock) og at flere utviklere kan jobbe parallelt.
:::

## Vanlige feil

- Kopiere og lime inn, og så endre litt.
- Funksjoner som både regner, skriver ut og lagrer.
- Navn som `f1`, `tmp`, `data2`.
- Kommentarer som gjentar koden (`x = x + 1  # øker x`).
- Overgeneralisering: lage noe «fleksibelt» som ingen trenger.
- Refaktorere uten tester.

## Huskeliste

- Gjenbruk: funksjoner, klasser, moduler, biblioteker.
- Parametere = det som varierer. Returverdi = resultatet.
- Abstraksjon: hva, ikke hvordan.
- DRY – én regel ett sted. KISS – enkelt nok for behovet.
- Høy kohesjon, lav kobling.
- Refaktorering: små steg, samme oppførsel, tester før og etter.
- Gode navn + docstring (formål, parametere, retur, begrensninger).
