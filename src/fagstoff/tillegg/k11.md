## Læringsmål

Etter dette kapittelet skal du kunne:

- forklare **bit** og **byte**, og hvorfor all data (tekst, bilder, lyd) må kodes som tall,
- regne om små binærtall til titallssystemet og forklare hva **heksadesimal** brukes til,
- forklare **tegnkoding** (ASCII, Unicode, UTF-8) og hvorfor «Ã¸» dukker opp i stedet for «ø»,
- beskrive **CSV**, **JSON** og **XML** – struktur, styrker og svakheter – og lese et eksempel på hver,
- **velge og begrunne** et format for en gitt situasjon,
- forklare **skjema/datakontrakt**, **validering**, **metadata** og **sporbarhet**, og hvorfor dato/tidssone må standardiseres.

> EKSAMEN: Kompetansemål 10 sier «gjøre rede for standarder». En standard er en **avtale** mellom systemer. Det beste svaret forklarer *hvorfor* avtalen trengs: «Hvis avsender og mottaker ikke er enige om format, feltnavn, datatyper og tegnkoding, blir dataene feiltolket.»

## Flere eksempler

### Eksempel 1 (enkelt): Binært

`1101₂` = 1·8 + 1·4 + 0·2 + 1·1 = **13**. Én byte (8 bit) kan ha 2⁸ = **256** ulike verdier (0–255). Fargen `#FF8800` i heksadesimal betyr rød = FF = 255, grønn = 88 = 136, blå = 00 = 0 – en oransje farge. Hvert heks-siffer er nøyaktig 4 bit, så to heks-siffer = én byte.

### Eksempel 2 (middels): Samme data i tre formater

```csv
id,navn,pris
1,"Skrivebord, eik",2499
2,Stol,799
```

```json
[
  {"id": 1, "navn": "Skrivebord, eik", "pris": 2499, "farger": ["eik", "hvit"]},
  {"id": 2, "navn": "Stol", "pris": 799, "farger": []}
]
```

```xml
<produkter>
  <produkt id="1"><navn>Skrivebord, eik</navn><pris>2499</pris></produkt>
  <produkt id="2"><navn>Stol</navn><pris>799</pris></produkt>
</produkter>
```

Legg merke til: i CSV må navnet med komma stå i **anførselstegn**, ellers blir det fire kolonner. Lister (farger) passer naturlig i JSON, men dårlig i CSV. I JSON er `2499` et tall og `"Stol"` tekst – i CSV er alt tekst til programmet tolker det.

### Eksempel 3 (sammensatt): Tegnkoding går galt

Et system lagrer «Bjørn» som UTF-8: ø blir de to bytene `C3 B8`. Et annet system leser filen som om den var Latin-1, der hver byte er ett tegn: `C3` = «Ã» og `B8` = «¸». Resultatet blir «BjÃ¸rn». Løsning: avtal UTF-8 overalt, og angi det eksplisitt: `open(fil, encoding="utf-8")` i Python og `Content-Type: application/json; charset=utf-8` i HTTP.

> FEIL: «JSON er sikkert fordi det er strukturert.» Nei – formatet sier ingenting om hvem som får lese dataene. Sikkerhet kommer fra tilgangskontroll og kryptering (kapittel 15).

## Gjennomarbeidet eksempel

**Oppgave:** En kommune skal utveksle innbyggerdata med flere etater. Hva må avtales?

1. **Format:** JSON via et API (strukturert, nestede data, godt støttet) – eller XML hvis etatene har eldre systemer med XML-skjema.
2. **Feltnavn og betydning:** `fodselsdato`, ikke `fdato` hos én og `birth` hos en annen. Hva betyr `status: 2`?
3. **Datatyper og formater:** dato som `2026-11-30` (ISO 8601), tidspunkt med tidssone (`2026-11-30T09:00:00+01:00`), beløp i øre eller kroner?
4. **Obligatoriske felt og tillatte verdier:** et **skjema** (JSON Schema/XSD) beskriver dette, så mottakeren kan **validere** automatisk.
5. **Tegnkoding:** UTF-8 (æ, ø, å og samiske tegn).
6. **Sikkerhet:** HTTPS, autentisering av etaten, autorisasjon (hver etat får bare feltene den trenger – dataminimering), logging.
7. **Dokumentasjon og versjonering:** endringer i formatet må varsles; gamle klienter må fortsatt virke.

Konklusjon: Uten slike avtaler blir data feiltolket, og feil kan få alvorlige konsekvenser for innbyggere (feil fødselsdato, feil ytelse).

## Praktisk demonstrasjon

Les en JSON-tekst i Python og valider innholdet:

```python
import json

tekst = '{"navn": "Sara", "alder": "19"}'
try:
    person = json.loads(tekst)
except json.JSONDecodeError:
    print("Ugyldig JSON")
else:
    alder = person.get("alder")
    if not isinstance(alder, int):
        print("Feil datatype for alder:", repr(alder))   # '19' er tekst!
```

Forklar: `json.loads` gjør teksten om til en ordbok. `get` unngår `KeyError` hvis feltet mangler. Typesjekken avslører at avsender sendte alder som tekst – et brudd på datakontrakten som ellers ville gitt feil sortering («9» > «19» alfabetisk).

## Muntlig forklaring

Prøv selv: Sammenlign CSV og JSON og si når du velger hva.

:::modell
«CSV er et tekstformat for tabeller: én rad per linje og felt skilt med komma eller semikolon. Det er enkelt, lett å åpne i regneark og passer til flate data som målinger eller en elevliste. Svakhetene er at datatyper ikke er definert, at komma i en verdi må håndteres med anførselstegn, og at lister og nestede strukturer passer dårlig. JSON lagrer objekter med nøkkel–verdi-par og lister, og har tall, tekst, sannhetsverdier og null. Det passer for strukturerte data og er standard i web-API-er. Hvis jeg skal lagre temperaturmålinger per time, velger jeg CSV. Hvis jeg skal lagre produkter med flere bilder og varianter, eller sende data mellom en app og en server, velger jeg JSON. I begge tilfeller må avsender og mottaker være enige om feltnavn, enheter og tegnkoding, helst UTF-8.»
:::

## Sensoroppfølging

1. «Hvorfor bør man bruke et CSV-bibliotek i stedet for `split(',')`?» – Verdier kan inneholde komma i anførselstegn, linjeskift.
2. «Hva er UTF-8?» – En koding av Unicode der vanlige tegn bruker 1 byte og andre (æøå) bruker flere.
3. «Hva er metadata?» – Data om data: kilde, tidspunkt, enhet, versjon, eier.
4. «Hvorfor validere på serveren når nettleseren allerede gjør det?» – Klientkode kan manipuleres.
5. «Når passer XML?» – Dokumenter og eldre integrasjoner med skjema/validering.

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Hva er en bit og en byte?
:::losning
En bit er den minste dataenheten og har verdien 0 eller 1. En byte er 8 bit og kan representere 256 ulike verdier (0–255), for eksempel ett tegn i ASCII. Større mengder måles i kilobyte, megabyte osv.
:::

:::oppgave Grunnleggende
2. Forklar hva CSV og JSON brukes til.
:::losning
CSV brukes til tabellformede data – eksport fra regneark, datasett med målinger, enkle lister. JSON brukes til strukturerte data med objekter og lister, særlig utveksling mellom programmer (web-API-er), konfigurasjonsfiler og lagring av nestede data.
:::

:::oppgave Middels
3. Velg mellom CSV og JSON for å lagre en liste over produkter med flere bilder og varianter. Begrunn.
:::losning
JSON. Hvert produkt har en **liste** med bilder og en liste med varianter (størrelse, farge, lagerstatus) – nestede data som JSON representerer direkte. I CSV måtte vi enten pakke flere verdier inn i ett felt (`"bilde1.jpg;bilde2.jpg"`) eller lage flere filer med koblinger – tungvint og feilutsatt. JSON har dessuten datatyper. Ulempen er at JSON må valideres mot en avtalt struktur, og ved mange samtidige oppdateringer bør produktene heller ligge i en database.
:::

:::oppgave Middels
4. Hvorfor kan tegn vises feil når data utveksles mellom systemer?
:::losning
Tegn lagres som tall etter en tegnkoding. Hvis avsender koder med UTF-8 og mottaker leser som Latin-1 (eller omvendt), tolkes bytene som andre tegn – «ø» blir «Ã¸». Løsningen er å avtale tegnkoding (UTF-8) og angi den eksplisitt ved lesing, skriving og i HTTP-headere.
:::

:::oppgave Utfordrende
5. En kommune skal utveksle innbyggerdata med flere etater. Drøft hvorfor format, feltnavn, datatyper, validering, sikkerhet og dokumentasjon må være avtalt.
:::losning
Se det gjennomarbeidede eksempelet. Kjernen: uten avtalt **format** kan mottaker ikke lese; uten avtalte **feltnavn** og betydning blir data misforstått; uten **datatyper/formater** (dato, tidssone, beløp) blir verdier feiltolket; uten **validering** slipper feil inn; uten **sikkerhet** (HTTPS, tilgang, dataminimering) lekker sensitive data; uten **dokumentasjon/versjonering** slutter integrasjoner å virke når noe endres. Konsekvensene rammer innbyggerne.
:::

## Vanlige feil

- Å tro at CSV har datatyper («tallet 007 ble til 7»).
- Å splitte CSV på komma manuelt.
- Å glemme tegnkoding når man åpner filer.
- Å bruke JSON «fordi det er moderne» uten å begrunne.
- Å blande format og sikkerhet.
- Lokal tid uten tidssone i data som utveksles.

## Huskeliste

- Bit = 0/1, byte = 8 bit = 256 verdier. Heks: 1 siffer = 4 bit.
- Unicode = tegnsett, UTF-8 = koding. Bruk UTF-8 konsekvent.
- CSV: flate tabeller, enkelt, ingen typer, pass på skilletegn.
- JSON: objekter og lister, typer, web-API.
- XML: tagger, skjema, dokumenter/eldre systemer.
- Database: relasjoner, mange brukere, spørringer.
- Standard = avtale: format, feltnavn, typer, tegnkoding, validering, sikkerhet, dokumentasjon.
