## Flere eksempler

### Eksempel 1 (enkelt): Sortering og filtrering

```sql
SELECT tittel, forfatter
FROM Bok
WHERE tilgjengelig = 1
ORDER BY tittel;
```

Les høyt: «Hent tittel og forfatter fra tabellen Bok, bare bøker som er tilgjengelige, sortert alfabetisk på tittel.»

### Eksempel 2 (middels): Mange-til-mange med koblingstabell

Elever kan ta mange fag, og et fag har mange elever.

| Elev | | Fag | | ElevFag | |
|---|---|---|---|---|---|
| **elev_id** (PK) | navn | **fag_id** (PK) | navn | elev_id (FK) | fag_id (FK) |
| 1 | Sara | 10 | IT2 | 1 | 10 |
| 2 | Ali | 11 | Matematikk R1 | 1 | 11 |
| | | | | 2 | 10 |

```sql
SELECT Elev.navn, Fag.navn
FROM Elev
JOIN ElevFag ON Elev.elev_id = ElevFag.elev_id
JOIN Fag ON Fag.fag_id = ElevFag.fag_id
WHERE Fag.navn = 'IT2';
```

Resultat: Sara og Ali. Koblingstabellen kan også få egne kolonner, f.eks. `karakter` – akkurat som en koblingsklasse i UML.

### Eksempel 3 (sammensatt): SQL-injeksjon og løsningen

```python
# FARLIG: brukerens tekst settes rett inn i SQL
sok = input("Søk: ")             # angriper skriver:  ' OR '1'='1
sql = "SELECT * FROM Kunde WHERE navn = '" + sok + "'"
# blir: SELECT * FROM Kunde WHERE navn = '' OR '1'='1'  -> alle kunder!

# TRYGT: parameterisert spørring
cursor.execute("SELECT * FROM Kunde WHERE navn = ?", (sok,))
```

Med parameter behandles input alltid som **data**, aldri som en del av SQL-koden.

## Gjennomarbeidet eksempel

**Oppgave:** Et system lagrer kundens navn og adresse i hver ordre. Hva er problemet, og hvordan modellerer vi bedre?

**Dagens tabell:**

| ordre_id | kundenavn | adresse | dato | total |
|---:|---|---|---|---:|
| 1 | Sara Lie | Storgata 1 | 2026-11-01 | 499 |
| 2 | Sara Lie | Storgata 1 | 2026-11-12 | 199 |
| 3 | Sara  Lie | Storgt. 1 | 2026-11-20 | 99 |

**Problemer:**
- *Duplisering:* samme navn og adresse gjentas i hver ordre.
- *Oppdateringsfeil:* Sara flytter – hvilke rader skal endres? Glemmer vi én, har vi motstridende data (inkonsistens).
- *Ulik skrivemåte:* rad 3 ser ut som en annen kunde.
- *Sletting:* sletter vi Saras eneste ordre, mister vi også opplysningene om henne.

**Bedre modell (normalisert):**

```text
Kunde(kunde_id PK, navn, adresse)
Ordre(ordre_id PK, kunde_id FK -> Kunde, dato, total)
```

```sql
SELECT Kunde.navn, Ordre.dato, Ordre.total
FROM Ordre
JOIN Kunde ON Kunde.kunde_id = Ordre.kunde_id
WHERE Kunde.kunde_id = 1;
```

Nå oppdateres adressen **ett sted**. Merk en nyanse: leveringsadressen *på selve ordren* kan det være riktig å lagre (hvor ble pakken sendt?) – det er en bevisst historikk, ikke duplisering. Å kunne si dette viser nivå 4.

## Praktisk demonstrasjon

Tegn tabellene for et utlånssystem på papir med PK og FK, og skriv tre spørringer:

```sql
-- 1. Alle bøker som er utlånt nå
SELECT Bok.tittel FROM Bok
JOIN Lan ON Lan.bok_id = Bok.bok_id
WHERE Lan.innlevert = 0;

-- 2. Registrer innlevering
UPDATE Lan SET innlevert = 1 WHERE lan_id = 42;

-- 3. Forfalte lån med medlemsnavn
SELECT Medlem.navn, Bok.tittel, Lan.frist
FROM Lan
JOIN Medlem ON Medlem.medlem_id = Lan.medlem_id
JOIN Bok ON Bok.bok_id = Lan.bok_id
WHERE Lan.innlevert = 0 AND Lan.frist < DATE('now');
```

Forklar hvorfor `WHERE lan_id = 42` er livsviktig i spørring 2.

## Muntlig forklaring

Prøv selv: Forklar primærnøkkel og fremmednøkkel med et eksempel.

:::modell
«En primærnøkkel er en kolonne som identifiserer hver rad unikt, for eksempel kunde_id i tabellen Kunde. To kunder kan hete Sara Lie, men de har ulik kunde_id. En fremmednøkkel er en kolonne i en annen tabell som peker på en primærnøkkel – Ordre har kunde_id som viser hvilken kunde ordren tilhører. Da trenger vi ikke kopiere navn og adresse inn i hver ordre, og når kunden flytter, oppdaterer vi bare én rad. Databasen kan også håndheve at en ordre ikke kan peke på en kunde som ikke finnes – det kalles referanseintegritet. Med JOIN kan jeg hente kundens navn sammen med ordrene når jeg trenger det.»
:::

## Sensoroppfølging

1. «Hva skjer med `DELETE FROM Kunde;` uten `WHERE`?» – Alle rader slettes; derfor backup og kontroll.
2. «Hvorfor trengs en koblingstabell?» – Mange-til-mange kan ikke lagres med én fremmednøkkel.
3. «Hva er en transaksjon?» – Flere operasjoner som én enhet: alt eller ingenting.
4. «Hvorfor database og ikke JSON-fil her?» – Relasjoner, samtidige brukere, integritet, spørringer.
5. «Hvordan forhindrer du SQL-injeksjon?» – Parameteriserte spørringer, validering, minste privilegium.

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Hva er en primærnøkkel og fremmednøkkel?
:::losning
Primærnøkkel: kolonne (eller kombinasjon) som unikt identifiserer hver rad i en tabell, f.eks. `kunde_id`. Fremmednøkkel: kolonne som refererer til primærnøkkelen i en annen tabell, f.eks. `Ordre.kunde_id`, og som binder tabellene sammen.
:::

:::oppgave Grunnleggende
2. Hva gjør `SELECT` og `WHERE`?
:::losning
`SELECT` velger hvilke kolonner som skal hentes (`SELECT navn, epost`). `WHERE` filtrerer hvilke rader som tas med (`WHERE kunde_id = 1`). Sammen med `FROM` (hvilken tabell) blir det en spørring.
:::

:::oppgave Middels
3. Lag en enkel tabellmodell for kunder og ordre.
:::losning
`Kunde(kunde_id PK, navn, epost)` og `Ordre(ordre_id PK, kunde_id FK, dato, status)`. Hvis ordre har flere varer: `Ordrelinje(ordre_id FK, produkt_id FK, antall, pris)` og `Produkt(produkt_id PK, navn, pris)`. Én kunde – mange ordre; én ordre – mange ordrelinjer.
:::

:::oppgave Middels
4. Forklar hvorfor mange-til-mange-relasjoner ofte trenger en koblingstabell.
:::losning
En kolonne kan bare holde én verdi per rad. Skal en elev ha mange fag og et fag mange elever, kan vi ikke legge én `fag_id` i elevtabellen eller én `elev_id` i fagtabellen. En koblingstabell `ElevFag(elev_id, fag_id)` har én rad per kobling, og kan i tillegg lagre data om koblingen (karakter, startdato).
:::

:::oppgave Utfordrende
5. Et system lagrer kundens navn og adresse i hver ordre. Forklar hvilke problemer det kan gi, og foreslå en bedre modell.
:::losning
Se det gjennomarbeidede eksempelet: duplisering, oppdateringsfeil/inkonsistens, ulik skrivemåte, tap av data ved sletting. Bedre: egen `Kunde`-tabell og fremmednøkkel fra `Ordre` (normalisering). Nyanse: leveringsadresse på ordretidspunktet kan lagres bevisst som historikk.
:::

:::oppgave Utfordrende
6. Forklar hvordan en bankoverføring kan bli inkonsistent uten transaksjoner.
:::losning
Overføring av 1000 kr = (1) trekk 1000 fra konto A, (2) legg 1000 til konto B. Hvis systemet krasjer etter (1) men før (2), er 1000 kr forsvunnet. Hvis to overføringer fra A skjer samtidig, kan begge lese saldo 1500 og begge godkjennes, så A ender på −500. En transaksjon gjør (1) og (2) **atomisk** (alt eller ingenting), sikrer at regler holder (konsistens), isolerer samtidige transaksjoner og gjør bekreftede endringer varige (ACID).
:::

## Vanlige feil

- `UPDATE`/`DELETE` uten `WHERE`.
- Lagre samme opplysning i mange tabeller.
- Mange-til-mange uten koblingstabell.
- Bygge SQL med strengsammenslåing av brukerinput.
- Tro at primærnøkkel må være navn eller e-post (de kan endres).
- Glemme at JOIN-betingelsen må koble riktig FK til riktig PK.

## Huskeliste

- Tabell = entitet, rad = post, kolonne = felt.
- PK identifiserer, FK peker.
- 1–1, 1–mange, mange–mange (koblingstabell).
- SELECT/FROM/WHERE/ORDER BY, INSERT, UPDATE … WHERE, DELETE … WHERE, JOIN … ON.
- Normalisering: ett faktum ett sted.
- Transaksjon og ACID: atomisk, konsistent, isolert, varig.
- Parameteriserte spørringer mot SQL-injeksjon.
