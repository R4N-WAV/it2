## Læringsmål

Etter dette kapittelet skal du kunne:

- forklare **klient**, **server**, **ruter**, **IP-adresse**, **DNS** og **protokoll**,
- beskrive hva som skjer fra du skriver en nettadresse til siden vises,
- forklare en **HTTP-forespørsel** (metode, adresse, headere, body) og et **svar** (statuskode, headere, body),
- bruke **GET, POST, PUT, PATCH, DELETE** riktig og forklare de vanligste **statuskodene** (200, 201, 400, 401, 403, 404, 500),
- forklare hva **HTTPS/TLS** beskytter – og hva det *ikke* beskytter,
- forklare hva et **API** er, og beskrive dataflyten i en app som henter JSON fra et API,
- forklare **timeout**, **retry**, **idempotens**, **caching** og hvorfor **API-nøkler** ikke skal ligge i klientkode.

## Flere eksempler

### Eksempel 1 (enkelt): Fra adresse til nettside

1. Du skriver `www.example.no` i nettleseren (**klienten**).
2. **DNS** oversetter navnet til en **IP-adresse**.
3. Nettleseren åpner en sikker forbindelse (**TLS**) til serveren.
4. Den sender `GET /` over **HTTPS**.
5. **Rutere** videresender pakkene gjennom mange nettverk.
6. **Serveren** svarer `200 OK` med HTML.
7. Nettleseren ber om bilder, CSS og skript med flere forespørsler og tegner siden.

### Eksempel 2 (middels): REST-lignende API for gruppetimer

| Handling | Metode og adresse | Typisk svar |
|---|---|---|
| Hent alle timer | `GET /api/timer` | `200` + JSON-liste |
| Hent én time | `GET /api/timer/17` | `200`, eller `404` hvis den ikke finnes |
| Book plass | `POST /api/timer/17/bookinger` | `201 Created`, eller `409`/`400` hvis full |
| Avbestill | `DELETE /api/bookinger/88` | `204`/`200` |
| Ikke innlogget | hvilken som helst | `401` |
| Innlogget, men andres booking | `DELETE /api/bookinger/91` | `403` |

**401 vs. 403:** 401 = «vi vet ikke hvem du er» (autentisering mangler). 403 = «vi vet hvem du er, men du har ikke lov» (autorisasjon).

### Eksempel 3 (sammensatt): Robust henting av værdata

```python
import json
import urllib.request

def hent_temperatur(by):
    url = f"https://api.example.no/vaer?by={by}"
    try:
        with urllib.request.urlopen(url, timeout=5) as svar:
            if svar.status != 200:
                return None, f"Tjenesten svarte {svar.status}"
            data = json.loads(svar.read().decode("utf-8"))
    except (OSError, json.JSONDecodeError):
        return None, "Fikk ikke kontakt med værtjenesten. Prøv igjen senere."
    temp = data.get("temperature")
    if not isinstance(temp, (int, float)):
        return None, "Ugyldige data fra tjenesten"
    return temp, None
```

Robusthet: **timeout** (henger ikke for alltid), sjekk av **statuskode**, håndtering av nettverksfeil og ugyldig JSON, **validering** av feltet, og en feilmelding brukeren forstår.

## Gjennomarbeidet eksempel

**Oppgave:** En app lagrer en API-nøkkel direkte i JavaScript-koden som sendes til nettleseren. Vurder risikoen og foreslå en tryggere arkitektur.

1. **Hva skjer:** All kode som kjører i nettleseren, kan leses av brukeren (Vis kilde, utviklerverktøy). Nøkkelen er dermed **offentlig**.
2. **Risiko:** Hvem som helst kan kopiere nøkkelen og bruke API-et i appens navn → kostnader (betalt API), at kvoten brukes opp (tilgjengelighet), misbruk av data nøkkelen gir tilgang til, og at leverandøren stenger kontoen. Ligger den i et offentlig Git-repo, finnes den i historikken selv om den slettes.
3. **Tryggere arkitektur:**

```diagram
boks klient 0 0 Nettleser (ingen nøkkel)
boks egen 1 0 Egen server / proxy
boks api 2 0 Ekstern API
pil klient egen : GET /vaer?by=Oslo
pil egen api : + API-nøkkel (hemmelig)
```

Nøkkelen ligger som en **miljøvariabel** på egen server, som legger den på forespørselen. Serveren kan også begrense bruk (rate limiting), cache svar og logge misbruk.
4. **Tiltak hvis nøkkelen har lekket:** roter (lag ny og deaktiver gammel) med en gang.

## Muntlig forklaring

Prøv selv: Forklar hva et API er og hvordan en vær-app bruker det.

:::modell
«Et API er et grensesnitt som lar ett program bruke data eller funksjoner fra et annet, uten å vite hvordan det er laget innvendig. En vær-app har ikke egne målestasjoner; den sender en HTTP-forespørsel, for eksempel GET med byen som parameter, til værtjenestens API. Serveren svarer med en statuskode – 200 hvis alt gikk bra – og data i JSON, som temperatur og enhet. Appen sjekker statuskoden, leser JSON-en, kontrollerer at temperaturen faktisk er et tall, og viser den. Hvis tjenesten ikke svarer, bruker appen en timeout og viser en forståelig melding, kanskje med sist lagrede verdi. Forbindelsen går over HTTPS, så dataene er kryptert underveis, og en eventuell API-nøkkel ligger på serveren, ikke i appen.»
:::

## Sensoroppfølging

1. «Hva gjør DNS?» – Oversetter domenenavn til IP-adresser.
2. «Gjør HTTPS appen sikker?» – Beskytter overføringen (kryptering, integritet, serverautentisering), ikke serverlogikk, tilgangskontroll eller lagring.
3. «Hvorfor er det farlig å prøve et betalingskall på nytt?» – Kan belaste flere ganger; krever idempotens (f.eks. unik ordre-ID).
4. «Hva er caching – og ulempen?» – Midlertidig kopi for fart; kan gi utdaterte data.
5. «Synkron vs. asynkron?» – Vente på svar vs. fortsette og håndtere svaret når det kommer (UI fryser ikke).

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Forklar forskjellen mellom klient og server.
:::losning
Klienten ber om en tjeneste (nettleser, app). Serveren tilbyr tjenesten og svarer (webserver, databaseserver). Én server betjener ofte mange klienter; data og regler kan dermed samles og beskyttes sentralt.
:::

:::oppgave Grunnleggende
2. Hva gjør DNS?
:::losning
DNS (Domain Name System) oversetter lesbare domenenavn som `udir.no` til IP-adresser som datamaskiner bruker for å finne hverandre – som en telefonkatalog for internett.
:::

:::oppgave Grunnleggende
3. Hva er et API?
:::losning
Et Application Programming Interface: en avtalt måte et program kan bruke funksjoner eller data fra et annet system på. Et web-API tilbyr adresser (endepunkter) som svarer på HTTP-forespørsler, ofte med JSON.
:::

:::oppgave Middels
4. Forklar hvorfor HTTPS er tryggere enn HTTP på åpne nettverk.
:::losning
På et åpent Wi-Fi kan andre lytte på trafikken. Med HTTP går passord og data i klartekst og kan leses eller endres underveis. HTTPS bruker TLS som krypterer trafikken (konfidensialitet), oppdager endringer (integritet) og bekrefter at du snakker med riktig server via sertifikat (autentisering).
:::

:::oppgave Middels
5. Beskriv hvordan en vær-app kan hente data fra et API og vise temperaturen.
:::losning
Se modellforklaringen og eksempel 3: GET-forespørsel med by → sjekk statuskode → parse JSON → valider temperatur → vis med enhet → håndter timeout/feil med forståelig melding (og eventuelt cache sist kjente verdi).
:::

:::oppgave Utfordrende
6. En app lagrer en API-nøkkel direkte i JavaScript-koden som sendes til nettleseren. Vurder risikoen og foreslå en tryggere arkitektur.
:::losning
Se det gjennomarbeidede eksempelet: nøkkelen er offentlig → misbruk, kostnader, tapt kvote, mulig datatilgang. Løsning: egen server/proxy som holder nøkkelen i en miljøvariabel, begrenser bruk og logger; rotér nøkkelen hvis den har lekket; aldri i offentlig repo.
:::

:::oppgave Utfordrende
7. Et bestillingssystem får 500-feil ved betaling. Forklar hvordan du ville undersøkt problemet, og hvilke logger og kontroller som kan være relevante.
:::losning
500 betyr feil på serveren, ikke hos brukeren. (1) Gjenskap: skjer det for alle eller bare enkelte betalingsmetoder/beløp? (2) Les **serverloggen** for tidspunktet: stack trace/feilmelding. (3) Sjekk **betalingsleverandørens** status og svar (timeout? endret API?). (4) Sjekk **databasen**: feilet lagring av ordre? (5) Sjekk nylige **endringer/deploy** (regresjon). (6) **Viktig kontroll:** ble kunden belastet selv om ordren feilet? Sammenstill betalinger og ordre, og sørg for idempotens så retry ikke belaster dobbelt. Logger må ikke inneholde kortnummer. Etter retting: test og overvåk.
:::

## Vanlige feil

- Blande 401 og 403.
- Tro at HTTPS gjør hele systemet sikkert.
- Ingen timeout eller feilhåndtering ved nettverkskall.
- Stole på data fra API-et uten validering.
- API-nøkler i klientkode eller i Git.
- Automatisk retry på operasjoner som ikke er idempotente.

## Huskeliste

- Klient spør, server svarer. DNS: navn → IP. Ruter videresender.
- HTTP: metode, adresse, headere, body. GET henter, POST oppretter, PUT/PATCH oppdaterer, DELETE sletter.
- 200 OK, 201 Created, 400 ugyldig, 401 ikke autentisert, 403 ikke tillatt, 404 finnes ikke, 500 serverfeil.
- HTTPS = HTTP + TLS: kryptering, integritet, serverautentisering.
- API: avtalt grensesnitt, ofte JSON.
- Robust klient: timeout, statuskode, validering, forståelig feilmelding, forsiktig retry (idempotens).
- Hemmeligheter på serveren.
