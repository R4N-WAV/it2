## Læringsmål

Etter dette kapittelet skal du kunne:

- skille **syntaksfeil**, **kjøretidsfeil** og **logiske feil** og gi eksempel på hver,
- følge en **systematisk feilsøkingsprosess** (gjenskap → forventet/faktisk → minste eksempel → hypotese → én endring → test → regresjon),
- forklare **enhetstest**, **integrasjonstest**, **systemtest** og **akseptansetest**,
- bruke **normalverdier**, **grenseverdier**, **ugyldig input**, **ekvivalensklasser** og **tilstandsoverganger** til å velge testtilfeller,
- lage en **testplan** med input, forventet resultat, faktisk resultat og bestått/ikke bestått,
- skrive enkle tester med `assert`,
- forklare hvorfor testing **ikke kan bevise** at et program er feilfritt, og hva **testdekning**, **TDD**, **mock** og **feilrapport** er.

> EKSAMEN: «Hvordan vet du at programmet virker?» er det vanligste oppfølgingsspørsmålet i hele faget. Svar alltid med **konkrete testtilfeller**, ikke «jeg prøvde det og det funket».

## Flere eksempler

### Eksempel 1 (enkelt): Tre feiltyper i samme funksjon

```python
def snitt(liste)                 # syntaksfeil: mangler kolon
    return sum(liste) / len(liste)
```

```python
def snitt(liste):
    return sum(liste) / len(liste)

snitt([])                        # kjøretidsfeil: ZeroDivisionError
```

```python
def snitt(liste):
    return sum(liste) / 2        # logisk feil: deler alltid på 2
```

Den logiske feilen er farligst: `snitt([4, 6])` gir riktig svar (5), så en lat test oppdager den ikke. `snitt([3, 3, 3])` avslører den (gir 4.5 i stedet for 3).

### Eksempel 2 (middels): Ekvivalensklasser og grenser for innlogging

Regel: kontoen låses etter 5 feilede forsøk.

| Klasse | Testverdi | Forventet |
|---|---|---|
| Riktig passord første gang | 0 feil før | Innlogget, teller nullstilles |
| Under grensen | 4 feil, så riktig | Innlogget |
| På grensen | 5 feil | Låst |
| Over grensen | 6. forsøk med riktig passord | Fortsatt låst |
| Ugyldig input | Tomt passord | Feilmelding, teller **ikke** økt? (avklar krav!) |

Siste rad viser at testing ofte avdekker **uklare krav**.

### Eksempel 3 (sammensatt): Tilstandsoverganger for en bok

```diagram
oval tilg 0 0 Tilgjengelig
oval utl 1 0 Utlånt
oval forf 2 0 Forfalt
pil tilg utl : lån_ut()
pil utl tilg : lever_inn()
pil utl forf : frist passert
pil forf tilg : lever_inn() + gebyr
```

Tester: gyldige overganger (tilgjengelig → utlånt → tilgjengelig) **og** ugyldige: `lån_ut()` på en utlånt bok skal avvises; `lever_inn()` på en tilgjengelig bok skal gi advarsel.

## Gjennomarbeidet eksempel

**Feil:** I bibliotekprogrammet kan samme bok lånes ut to ganger.

1. **Gjenskap:** Opprett bok B, medlemmer A og C. Lån B til A. Lån B til C. → Systemet lager to lån.
2. **Forventet vs. faktisk:** Forventet at andre utlån avvises. Faktisk: nytt lån opprettes.
3. **Minste eksempel:** Feilen skjer også uten medlem C – A kan låne samme bok to ganger.
4. **Les koden:**

```python
def registrer_lan(self, medlem, bok):
    lan = Lan(medlem, bok)
    self.lan.append(lan)
    bok.tilgjengelig = False
```

5. **Hypotese:** Metoden sjekker aldri `bok.tilgjengelig` før den oppretter lånet.
6. **Én endring:**

```python
def registrer_lan(self, medlem, bok):
    if not bok.tilgjengelig:
        return None
    lan = Lan(medlem, bok)
    self.lan.append(lan)
    bok.tilgjengelig = False
    return lan
```

7. **Test på nytt + regresjon:**

```python
bib = Bibliotek()
b = Bok("Sofies verden")
assert bib.registrer_lan("A", b) is not None   # første lån lykkes
assert bib.registrer_lan("C", b) is None       # andre avvises
b.tilgjengelig = True                          # (simulerer innlevering)
assert bib.registrer_lan("C", b) is not None   # kan lånes igjen
```

8. **Refleksjon:** Med flere samtidige brukere må sjekken skje atomisk på serveren/databasen, ellers kan to forespørsler begge se «tilgjengelig». Det er en integrasjons-/samtidighetstest, ikke en enhetstest.

## Praktisk demonstrasjon

Lag en testplan **på papir** for `rabatt(pris)` (10 % fra og med 500 kr) og kjør den med `assert`:

```python
def rabatt(pris):
    if pris >= 500:
        return pris * 0.9
    return pris

tester = [(499, 499), (500, 450), (501, 450.9), (0, 0), (1000, 900)]
for inn, forventet in tester:
    faktisk = rabatt(inn)
    status = "OK" if abs(faktisk - forventet) < 0.001 else "FEIL"
    print(inn, forventet, faktisk, status)
```

Forklar høyt: «499, 500 og 501 tester grensen fra begge sider. 0 er en ytterverdi. Jeg sammenligner med en liten toleranse fordi desimaltall kan få avrundingsfeil. Jeg har ikke testet negativ pris – det bør avklares om det skal gi feil.»

## Muntlig forklaring

Prøv selv: Forklar hvordan du ville testet et program du har laget.

:::modell
«Jeg tester på flere nivåer. Først enhetstester av de viktigste funksjonene, for eksempel at bookingmetoden avviser når timen er full. Jeg velger testdata systematisk: en vanlig verdi, verdier rett under, på og over grensen – for kapasitet 10 tester jeg 9, 10 og 11 bookinger – og ugyldig input som tomt navn eller negativt tall. Jeg skriver forventet resultat før jeg kjører, og noterer faktisk resultat. Så tester jeg at delene virker sammen, for eksempel logikk og lagring, og til slutt lar jeg en bruker prøve en realistisk oppgave. Testing kan vise at det finnes feil, men ikke bevise at det ikke finnes noen, så jeg prioriterer de tilfellene der feil vil ha størst konsekvens. Når jeg retter en feil, kjører jeg de gamle testene på nytt – regresjonstesting – så jeg ikke ødelegger noe annet.»
:::

## Sensoroppfølging

1. «Hvilke tilfeller har du ikke testet?» – Vær ærlig og konkret: samtidighet, veldig store datamengder, spesialtegn.
2. «Hvorfor teste 499, 500 *og* 501?» – Feil skjer typisk ved grensen (`>` vs `>=`).
3. «Hva er en regresjonstest?» – Kjøre tidligere tester etter endring.
4. «Hva er forskjellen på enhetstest og akseptansetest?» – Liten isolert del vs. om løsningen dekker brukerens behov.
5. «Hvordan tester du noe som henter data fra et API?» – Mock med fast svar; test også feilsvar og timeout.

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Forklar forskjellen mellom syntaksfeil, kjøretidsfeil og logisk feil.
:::losning
**Syntaksfeil:** koden bryter språkets regler og kan ikke kjøres (manglende kolon, feil innrykk). **Kjøretidsfeil:** koden starter, men krasjer underveis (deling på null, fil finnes ikke, `IndexError`). **Logisk feil:** koden kjører uten feilmelding, men gir feil resultat (`>` i stedet for `>=`). Logiske feil oppdages bare med tester der vi vet forventet svar.
:::

:::oppgave Grunnleggende
2. Hvorfor er det viktig å teste verdier på begge sider av en grense?
:::losning
Fordi feil ofte ligger nøyaktig på grensen: en utvikler skriver `>` der kravet er `>=`. Tester man bare 300 og 800, går begge versjonene «bra». Tester man 499, 500 og 501, avsløres det om 500 havner i riktig gruppe.
:::

:::oppgave Middels
3. Lag en testplan for funksjonen som beregner rabatt: 0 % under 500 kr, 10 % fra og med 500 kr.
:::losning
| Test | Input | Forventet | Hvorfor |
|---|---:|---:|---|
| T1 | 0 | 0 | Ytterverdi |
| T2 | 250 | 250 | Normalverdi under grensen |
| T3 | 499 | 499 | Rett under grensen |
| T4 | 500 | 450 | På grensen (fra og med) |
| T5 | 501 | 450,90 | Rett over grensen |
| T6 | 1000 | 900 | Normalverdi over |
| T7 | -10 | Feil/avvis | Ugyldig input – avklar krav |

Kolonner for faktisk resultat og bestått fylles ut når testen kjøres.
:::

:::oppgave Middels
4. Forklar forskjellen mellom enhetstest, integrasjonstest og systemtest.
:::losning
Enhetstest: én funksjon/metode isolert (`rabatt(500) == 450`). Integrasjonstest: om flere deler virker sammen (bestillingslogikken lagrer riktig i databasen). Systemtest: hele systemet som helhet, gjennom grensesnittet, slik en bruker ville brukt det. (Akseptansetest: om løsningen oppfyller kravene til oppdragsgiver/bruker.)
:::

:::oppgave Utfordrende
5. Et bibliotekprogram lar brukeren låne samme bok flere ganger. Beskriv hvordan du vil gjenskape, undersøke, rette og teste feilen.
:::losning
Se det gjennomarbeidede eksempelet over: gjenskap med minst mulig data, skriv forventet/faktisk, finn at tilgjengelighet ikke sjekkes, rett med én endring, skriv tester som både første og andre utlån, kjør regresjonstester, og vurder samtidighet ved flere brukere.
:::

:::oppgave Utfordrende
6. Lag testtilfeller for et innloggingssystem som har maks fem forsøk før kontoen låses midlertidig. Ta med normalverdier, grenseverdier og ugyldig input.
:::losning
Normal: riktig passord første gang → innlogget. Grense: 4 feil + riktig → innlogget (og teller nullstilles); 5 feil → låst; 6. forsøk (riktig passord) → fortsatt låst. Tid: etter at låsetiden er ute → kan logge inn igjen. Ugyldig input: tomt brukernavn, tomt passord, svært lang tekst, spesialtegn/SQL-tegn (`' OR 1=1 --`) → avvises trygt. Andre: feil brukernavn skal gi samme melding som feil passord (ikke avsløre om brukeren finnes); to kontoer skal ha separate tellere.
:::

**Sensor kan spørre:** Hvordan vet du at programmet fungerer? Hvilke tilfeller har du ikke testet? Hva er forskjellen mellom forventet og faktisk resultat? Hvordan unngår du at en feil kommer tilbake?

## Vanlige feil

- «Jeg testet det, og det virket» – uten konkrete testtilfeller.
- Bare normalverdier, ingen grenser eller ugyldig input.
- Skriver forventet resultat *etter* å ha kjørt (da tester man ikke, man noterer).
- Endrer mange ting samtidig under feilsøking.
- Tror høy testdekning betyr feilfritt.
- Logger passord eller personopplysninger.

## Huskeliste

- Syntaks / kjøretid / logisk.
- Feilsøking: gjenskap → forventet/faktisk → minste eksempel → hypotese → én endring → test → regresjon.
- Nivåer: enhet → integrasjon → system → akseptanse.
- Teknikker: normal, grense (under/på/over), ugyldig, ekvivalensklasser, tilstander, regresjon.
- Testplan: hva, input, forventet, faktisk, bestått.
- Testing finner feil – beviser ikke feilfrihet.
- Mock erstatter eksterne tjenester i tester. TDD: test først.
