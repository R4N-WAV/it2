## Læringsmål

Etter dette kapittelet skal du kunne:

- beskrive fasene i **systemutvikling** og forklare at de i praksis overlapper og gjentas,
- sammenligne **fossefallsmodellen** og **smidig utvikling**, og **velge** metode for en konkret situasjon med begrunnelse,
- forklare **Scrum**: roller (Product Owner, Scrum Master, utviklere), artefakter (product backlog, sprint backlog, inkrement) og hendelser (sprint, sprint planning, daily scrum, review, retrospective),
- forklare **Git**-begrepene repository, commit, branch, merge, pull, push og **merge conflict**, og beskrive en arbeidsflyt for to utviklere,
- forklare hva god **dokumentasjon** og **samarbeidsavtaler** i et team inneholder,
- koble metode til verktøy: oppgavetavle (Kanban), versjonskontroll, kodegjennomgang (pull request), felles testsuite.

> EKSAMEN: Kompetansemål 9 sier «**velge og bruke**». Det holder ikke å kunne definere Scrum. Du må kunne si *hvorfor* du ville valgt Scrum (eller fossefall) for akkurat dette prosjektet, og *hvordan* teamet ville brukt Git i praksis.

## Flere eksempler

### Eksempel 1 (enkelt): Én sprint i bibliotekprosjektet

- **Product backlog** (prioritert av Product Owner): 1) registrere utlån, 2) innlevering, 3) søk, 4) varsel om forfalt frist, 5) statistikk.
- **Sprint planning:** teamet velger 1 og 2 for en to-ukers sprint og bryter dem ned i oppgaver.
- **Daily scrum** (15 min): hva gjorde jeg i går, hva gjør jeg i dag, hva hindrer meg?
- **Sprint review:** bibliotekarene prøver utlån og innlevering, og oppdager at de også må kunne *forlenge* lån → ny post i backloggen.
- **Retrospective:** «Vi testet for sent – neste sprint skriver vi testene sammen med koden.»

### Eksempel 2 (middels): Git-flyt for to utviklere

```text
git pull                              # hent siste versjon av main
git switch -c sok-etter-bok           # egen branch for funksjonen
# ... endre kode, kjør tester ...
git add sok.py test_sok.py
git commit -m "Legg til søk på tittel og forfatter"
git push -u origin sok-etter-bok      # del branchen
# lag pull request -> kollega gjør code review -> merge til main
```

Kollegaen jobber samtidig på `forfalt-varsel`. Fordi de bruker hver sin branch, forstyrrer de ikke hverandre før merge.

### Eksempel 3 (sammensatt): Merge conflict

Begge har endret samme linje i `bibliotek.py`:

```text
<<<<<<< HEAD
MAKS_LAN = 5
=======
MAKS_LAN = 3
>>>>>>> forfalt-varsel
```

Git kan ikke vite hvilken som er riktig. Utviklerne må **snakke sammen** (hva er kravet?), velge/kombinere, fjerne markørene, kjøre testene og committe. Konflikter reduseres med små, hyppige commits, korte brancher og tydelig arbeidsdeling.

### Eksempel 4: Fossefall i et prosjekt med faste krav

Et system for å beregne en offentlig avgift etter en lov som er vedtatt, med krav om dokumentert godkjenning i hver fase. Kravene er stabile og må være riktige før koding. Her kan fossefall (eller en hybrid med tydelige faser) passe.

## Gjennomarbeidet eksempel

**Oppgave:** Et team utvikler en app der kravene endrer seg hver uke. Velg arbeidsmetode og begrunn.

1. **Situasjonen:** ustabile krav, behov for tilbakemelding, risiko for å bygge feil ting.
2. **Fossefall?** Krever at kravene låses tidlig. Endringer sent blir dyre, og brukerne ser løsningen først til slutt → dårlig match.
3. **Smidig/Scrum?** Korte sprinter (1–2 uker) gir et fungerende inkrement som brukerne kan teste. Product Owner prioriterer backloggen på nytt hver sprint, så nye krav tas inn kontrollert. Review gir tilbakemelding, retrospective forbedrer prosessen.
4. **Risiko ved smidig:** mål kan skli, dokumentasjon kan forsømmes. **Tiltak:** tydelig produktmål, Definition of Done som inkluderer tester og dokumentasjon, og at bare Product Owner endrer prioriteringer.
5. **Verktøy:** oppgavetavle (to do / doing / done), Git med branches og pull requests, automatiske tester ved hver push.
6. **Konklusjon:** «Jeg velger Scrum fordi kravene endrer seg ofte og vi trenger tidlig tilbakemelding. Ulempen med mindre forutsigbarhet håndterer vi med et tydelig produktmål og en felles definisjon av ferdig.»

## Praktisk demonstrasjon

Tegn en **Scrum-tavle** og en **Git-graf** på papir for casen du har trukket:

```diagram
boks backlog 0 0 Backlog: søk, varsel, statistikk
boks todo 1 0 Sprint: utlån, innlevering
boks doing 2 0 Pågår: innlevering (Ali)
boks done 3 0 Ferdig: utlån (testet)
pil backlog todo : sprint planning
pil todo doing
pil doing done : Definition of Done
```

Forklar hvem som flytter kortene, hva «ferdig» betyr, og hvor Git kommer inn (hver oppgave = egen branch, merge etter review og grønne tester).

## Muntlig forklaring

Prøv selv: Sammenlign fossefall og smidig utvikling.

:::modell
«I fossefallsmodellen gjennomføres fasene i rekkefølge: krav, design, implementering, testing og levering. Fordelen er tydelig planlegging og dokumentasjon, og det passer når kravene er stabile og må godkjennes formelt. Ulempen er at brukerne ser løsningen sent, så misforståtte krav oppdages sent og blir dyre å rette. Smidig utvikling deler arbeidet i korte iterasjoner som hver gir noe som fungerer. I Scrum heter de sprinter; Product Owner prioriterer backloggen, teamet planlegger sprinten, har korte daglige møter, viser resultatet på sprint review og forbedrer samarbeidet på retrospektiven. Fordelen er rask tilbakemelding og at endringer kan tas inn. Ulempen er mindre forutsigbarhet og at dokumentasjon kan bli forsømt. For en app der brukerbehovene er uklare, ville jeg valgt Scrum; for et system med lovbestemte, faste krav kunne fossefall vært riktigere.»
:::

## Sensoroppfølging

1. «Hva gjør Product Owner?» – Eier og prioriterer backloggen, representerer brukernes behov.
2. «Er Scrum bare daglige møter?» – Nei: synlig arbeid, prioritering, korte leveranser, kontinuerlig forbedring.
3. «Er Git en backup?» – Ikke alene; trenger fortsatt backup-rutiner og tilgangskontroll.
4. «Hva er en god commit-melding?» – Kort, beskriver hva og hvorfor, én logisk endring.
5. «Hvordan sikrer dere kvalitet før merge?» – Pull request, code review, automatiske tester.

## Oppgaver og løsningsforslag

:::oppgave Grunnleggende
1. Forklar hva systemutvikling er.
:::losning
Hele prosessen med å planlegge, designe, utvikle, teste, innføre og vedlikeholde et informasjonssystem: forstå behovet, lage krav, modellere, programmere, teste, levere, lære opp brukere og videreutvikle. Fasene overlapper ofte og gjentas.
:::

:::oppgave Grunnleggende
2. Hva er en commit og en branch i Git?
:::losning
En **commit** er et lagret øyeblikksbilde av endringer med en beskrivende melding, slik at man kan se historikken og gå tilbake. En **branch** er en egen utviklingslinje der man kan jobbe med en funksjon uten å påvirke hovedversjonen, og som senere kan merges inn.
:::

:::oppgave Middels
3. Sammenlign fossefallsmodellen og smidig utvikling.
:::losning
Se modellforklaringen. Fossefall: faser i rekkefølge, forutsigbart og dokumentert, men sene endringer er dyre og brukere ser produktet sent. Smidig: korte iterasjoner, tidlig og hyppig tilbakemelding, tar inn endringer, men krever god kommunikasjon og kan gi lavere forutsigbarhet. Valg avhenger av hvor stabile kravene er.
:::

:::oppgave Middels
4. Forklar hvordan Scrum kan gjøre et utviklingsprosjekt mer oversiktlig.
:::losning
Arbeidet blir synlig i en prioritert backlog og på en sprinttavle; alle vet hva som skal gjøres nå og hva som er viktigst. Korte sprinter med mål gir hyppige kontrollpunkter. Daily scrum avdekker hindringer tidlig. Review viser faktisk fremdrift (fungerende programvare, ikke bare rapporter), og retrospektiven forbedrer måten teamet jobber på.
:::

:::oppgave Utfordrende
5. Et team utvikler en app der kravene endrer seg hver uke. Velg en passende arbeidsmetode og begrunn valget.
:::losning
Se det gjennomarbeidede eksempelet: Scrum med korte sprinter, Product Owner som prioriterer, review med brukere, Definition of Done med tester og dokumentasjon, Git med branches og pull requests. Begrunnelse: ustabile krav krever hyppig tilbakemelding og kontrollert endring.
:::

:::oppgave Utfordrende
6. To utviklere endrer samme fil på hver sin branch. Forklar hvordan versjonskontroll kan håndtere situasjonen, og hva en merge conflict innebærer.
:::losning
Hvis de har endret **ulike deler** av filen, slår Git sammen endringene automatisk ved merge. Hvis de har endret **samme linjer**, oppstår en merge conflict: Git markerer begge versjonene i filen, og et menneske må bestemme riktig innhold, fjerne markørene, teste og committe. Historikken viser hvem som endret hva. Forebygging: små commits, hyppig `pull`, korte brancher, tydelig arbeidsdeling og code review.
:::

## Vanlige feil

- Å beskrive Scrum som «bare møter».
- Å si «smidig er alltid best» uten å se på kravene.
- Å blande Product Owner og Scrum Master.
- Å tro at Git er backup.
- Store commits med meldingen «fikser».
- Å jobbe direkte på main uten review.

## Huskeliste

- Faser: behov → krav → design → implementering → test → levering → vedlikehold (overlappende).
- Fossefall: stabile krav, tydelige faser, dyre sene endringer.
- Smidig: korte iterasjoner, tilbakemelding, endringer underveis.
- Scrum: PO (prioriterer), SM (prosess, fjerner hindringer), utviklere; backlog, sprint, planning, daily, review, retro.
- Git: repo, commit, branch, merge, pull, push, conflict. Pull request + review.
- Dokumentasjon: krav, modeller, README, testplan, endringslogg.
